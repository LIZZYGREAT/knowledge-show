## 二、核心设计：“沿知识轨迹生长的事件星群”

页面保留清楚的三阶段导航，下面不再只有一条淡灰曲线，而是一片轻巧的**生成中的知识轨迹场**。主视觉随当前阶段改变状态，**节点是阶段，气泡是已触发的小事件，粒子是纯视觉的流动装饰**。

它应表达三个关系：

1. **当前阶段**：哪一段正在发生，视觉中心始终明确。顶部三个步骤与中央的“主节点”互相呼应。
2. **真实小事件**：发生一件事情，就在当前主节点旁冒出一个带短语义标签的气泡，沿一条柔和弧形轨迹弹出，轻微停留，逐渐缩小消散；再来新的事件时，形成短暂的连续流动。
3. **持续等待**：模型可能几十秒不返回任何事件。此时主节点仍以低频、低干扰的呼吸、轨道慢速流动表达“任务仍在进行”，**不能持续伪造“已完成 X”**。

### 1. 建议页面层级（桌面）

```text
┌──────────────────────────────────────────────────────────────────────────┐
│  CREATING YOUR VIDEO                                                   │
│  一个好奇的问题，正在变成一支动画。                                      │
│  为什么会出现生日悖论？                                                 │
│                                                                          │
│   ● 知识探索 ━━━━━━━ ● 脚本编排 ━━━━━━━ ○ 动画制作                      │
│     已完成            正在进行             即将开始                      │
│                                                                          │
│             ────╮                     ╭────────                          │
│       ·       [已选好讲述角度] ─╮    ·     ·                              │
│          ○          ╲          ◉ 脚本主节点          ·                    │
│      ·          [正在整理场景]  ╰────╮     [讲述顺序已整理]               │
│                  ·                ╰─────── ·                             │
│                                                                          │
│                   正在安排视频的讲述顺序                                │
│                最近一步：正在整理场景之间的衔接                         │

│                   返回创作页 / 失败时重试                               │

```

此示意只用于确定信息关系，**不要求把文字塞进大量流程方框**。动画主舞台须有精致的留白、线条、粒子与大小适中的标签，不能在中间做成三张长卡片轮播。

建议桌面主视觉区域高约 **300–370 px**，重要画面集中在中央可观看区域；顶部阶段指示应较为紧凑，减少两套进度信息的重复。移动端保持主节点、当前事件与最少装饰，简化曲线和离屏粒子。

### 2. 三个阶段分别如何呈现（同一语法，彼此不同）

| 阶段 | 主节点与轨迹含义 | 真实可显示的小事件（只有实际触发才出现） | 纯视觉运动 |
| --- | --- | --- | --- |
| **知识探索** | 若干细小知识点沿弧线逐渐靠近主节点，形成几条清晰关联 | “正在了解主题”“正在补充关键资料”“正在寻找讲述角度”“正在确认重要知识”“知识方向已准备好” | 小粒子沿不同方向柔和聚拢；完成时节点稳定着色 |
| **脚本编排** | 知识节点沿一条更有节奏的轨迹重新排列，形成连续叙事线 | “正在安排讲述顺序”“正在组织场景”“脚本方案已准备好”（按照后端真实可发事件） | 若干节点沿曲线移动并排序，线条轻微绘出；完成时不再散乱 |
| **动画制作** | 叙事轨迹逐渐转为有层次的画面片段、细线与帧的轮廓 | “正在制作动画场景”“第 2 段画面已准备好”“正在检查画面”“预览已准备好”（仅在执行器能确认时） | 片段轮廓轻微成形、光点连接；真实加载通过后进入完整态 |

三种阶段应该保持家族一致性，但核心图案和运动方向不同；不只是改变节点的颜色。**气泡文字来源于已发生的用户语义事件，而不是装饰性随机文本**。内部技术细节不要原样暴露。

### 3. 气泡的完整生命周期

建议每个事件气泡都有自己的稳定 UI ID，状态依次为：

`emerging → traveling → resting → dissolving → removed`

- **涌现**（约 300–450ms）：从当前阶段主节点附近低透明度出现，柔和缩放，从小光点生长为可阅读的圆角胶囊；不进行刺眼弹跳。
- **沿轨迹移动**（约 800–1200ms）：沿二次/三次贝塞尔路径向可读位置缓动，伴随少量小光点分离。轨迹可由已有 SVG path 实现，也可通过 CSS/GSAP MotionPath。**不要用匀速直线飞出。**
- **停留**（约 2.5–4s，长消息可略延长）：保证有时间读清楚，字不持续漂移。当前最重要事件也要同步展示在舞台下方的稳定文字位置。
- **消散**（约 600–900ms）：气泡边缘逐渐变淡，少量粒子沿原来运动方向散开，标签缩小淡出；使用 DOM 生命周期移除节点，不留下无限增长的元素。

这是**动效设计参考值**，实际以观感测试确定。一个时间点建议最多 2–3 条可读气泡，粒子总量在普通桌面维持 8–16 个，移动端更少。若事件密集，合并重复消息/快速消化排队，不创建无数重叠弹窗。

### 4. 轨迹与色彩

- **主路径**：一条温柔流动的非对称 S 形曲线，使用现有深绿/薄荷绿，金色只用于“关键节点”与完成时刻。
- **次级轨道**：2–3 条局部短弧或虚线，体现小事件来自当前阶段而非从页面任意位置出现。
- **粒子**：点、短划、微小光片，优先几何干净且清晰；不大量使用朦胧虚化、泛光或过暗透明度。
- **事件标签**：米白/浅纸色底、清晰对比文字、细边、淡阴影；**标签不应被漂浮动画持续晃动**。
- **阶段焦点**：主节点可随阶段变化从“聚合→排布→画面成形”，但整体位置相对稳定，避免用户眼睛来回追踪。

不要将三阶段分别做成科技加载条、三个巨大圆圈或三张可切换 PPT。优先让粒子的出现与消散表现“正在生成”的生命感。

## 三、事件数据与真实任务状态：最小接线方案

### 1. 必须区分两类信号

- **业务事件**：由知识/脚本/动画实际执行产生；有明确 `stage`、发生时间、语义和单调递增 ID。只有这些事件才能生成“正在处理/已完成某项”的文字气泡。
- **环境动效**：不表达真实完成进度，纯粹让等待画面保持轻柔运动；可以按时间循环，但不得生成“已完成一个步骤”的假文案、虚假数量或百分比。

现有 `JobSnapshot` 只有 `status/current_stage/stages/message/artifacts`；`backend/src/api/task_runner.py::on_event` 会用 `_stage_message(stage, state)` 覆盖每条细分的语义。因此只改前端会导致“随机气泡看似有内容、实际上毫无信息”。建议在**现有任务快照上增加一个可选、有限、经过安全封装的事件摘要数组**；保持原字段不变。

### 2. 建议轻量兼容字段（只属于任务 API，不改五类产物 Schema）

```json
{
  "job_id": "JOB_example",
  "status": "running",
  "current_stage": "knowledge",
  "message": "正在寻找有趣的讲述角度",
  "display_events": [
    {"seq": 4, "stage": "knowledge", "code": "knowledge.research", "text": "正在了解这个主题"},
    {"seq": 5, "stage": "knowledge", "code": "knowledge.creative", "text": "正在寻找有趣的讲述角度"}
  ]
}
```

这里只是**建议的增量响应示例**，保留现有任务 JSON 的所有字段。约束：

1. 事件序号由后端按当前 Job 单调递增，便于轮询去重；只保留最近 **8–12 条**可展示事件。重复的相同 `code/text` 不反复追加。
2. `display_events` **只含白名单字段** `seq/stage/code/text`（可选 timestamp）。绝不写入 `diagnostic`、原始 Research/Verifier 回复、Query、Prompt、URLs、API Key、tokens、金额、完整知识包等。
3. 映射层使用 `backend/src/workflow/service.py::_relay_knowledge_event/_relay_script_event` 已有的语义与阶段，不需要让前端阅读复杂的 Agent 内部事件。
4. 业务阶段完成只能由**现有已发布 ArtifactRef 的逻辑**认定：知识 `delivery` 真正发布、脚本校验发布、动画资源通过实际播放检查。不能因为气泡播放到最后一条就将阶段设为 completed。
5. 所有新增 UI 事件是**可选的**；旧 Job JSON 没有该数组时继续展示真实的 `message`，不得渲染异常页面。
6. 几十秒没有新事件时，持续呈现“正在处理”的环境动效与当前稳定文案，不添加“已找到三个有趣知识点”等虚构内容。

**最低成本版本**：先不改公共 Schema 或引入消息流服务，只修改 `backend/src/api/task_runner.py` 的事件白名单收集、`backend/src/workflow/jobs.py` 的有限列表存取，以及前端 `JobSnapshot` 类型与适配器。

### 3. 动画阶段的事件来源

`AnimationHandoff.tsx` 另行轮询 `/animations/jobs/{job_id}`；其状态与知识脚本任务不是同一 Job。主舞台的事件融合必须明确两个来源：

- Knowledge/Script：来自当前 `jobId` 的安全 `display_events`。
- Animation：来自当前 `animationJobId` 的安全阶段/场景事件，缺少事件列表时仅使用其真实 `status/message`；绝不能利用上游 Job 的 `script_ready` 误称动画完成。

建议先在 `backend/src/animation/api.py` 的动画 Job 快照加入同一**显示事件摘要格式**；`AnimationService.generate()` 增加很薄的可选 `on_progress` 回调，在**某幕确实生成或从有效缓存恢复之后**发出 `animation.scene_ready`。只有真实渲染检查已通过才发 `animation.preview_ready`。首次未接入幕级事件时，主舞台仍可通过动画任务 `queued/running/failed` 正确显示，**不强行模拟**每幕完成。

不要把模型内部 `SceneContext`、编译器异常、临时资源 key 和原始场景 JSON 写进事件文字。动画片段可以用“第 2 段画面已准备好”这样的自然语言；如使用脚本场景名，需取可信业务文本、限制长度，避免将敏感/技术字段带给用户。

### 4. 前端事件消费规则

建议单独封装 UI 适配器（例如扩展 `frontend/src/common/progress.ts`）：

```ts
type DisplayEvent = {
  seq: number;
  stage: "knowledge" | "script" | "animation";
  code: string;
  text: string;
};

// UI 内部身份：`${jobId}:${seq}`；动画任务使用自己的 animationJobId。
// 旧 Job 缺事件列表时，只显示真实 stage/message，不合成假的里程碑。
```

- 轮询多次得到同一事件时只展示一次；组件重新渲染不会反复触发 `enter`。
- 任务切换、重新生成、恢复旧会话时，根据 `jobId/animationJobId` 重置当前动画队列，不能让上一作品的气泡混入。
- 页面刷新后可以将最近 1–2 条已完成事件作为**静态“最近进展”**展现，不必回放数分钟内全部动画。真正的新事件才触发弹出。
- 同时到来多条可展示事件时按 `seq` 排队；首屏新进入尽量先显示最新重要进展，队列有上限。
- 失败/中断时停止不相关的完成动画，主节点保留当前阶段位置，显示稳定的错误状态和已有重试操作；成功时主节点自然过渡到下一阶段。
- 视频真正可预览前，动画状态不能仅凭 `animationJob.status=completed` 就显示“成片可播放”；以 `preview.status=ready` 且实际 bundle 加载成功为准，沿用现有检查。

### 1. 动态布局与避免遮挡

- 主节点与轨道位于动画区域中央，小事件气泡使用约 3 个**受控停靠区域**，不同事件按 seq 轮转，避免直接随机定位和相互覆盖。
- 气泡允许有不同入场轨迹（例如左上短弧、右上宽弧、下方回弧），路径从当前主节点出发；轨迹可以用固定贝塞尔模板微调，而不是运行复杂碰撞物理引擎。
- 活跃气泡最多 3 个，文字短、行高合理；最近一条重要信息在下方稳定显示。不要让唯一的状态文案随着气泡消散而失去可读性。
- 主视觉不覆盖顶部进度条、主题、按钮或脚本预览；所有飞出的元素裁剪在动画区域内。
- 页面窄于约 760px 时改为单主节点 + 1–2 个可见气泡、缩短轨迹，禁止文字溢出。

### 2. 减少动效与性能

- 尊重 `prefers-reduced-motion`：不播放粒子飞行、缩放、持续漂浮；直接展示当前节点与最近两条真实事件的静态文字。
- 标签页失焦或不可见时停止纯装饰动画的帧更新；返回页面时恢复当前状态，不快速补放积压的几十个动画。
- 尽量只动画 `transform`、`opacity`、SVG 少量属性，不每帧重建整棵 React 树，不创建几百个 SVG/DOM 节点。
- 低端设备优先保证页面、API 轮询和错误按钮可用；视觉组件异常不应影响任务执行。
- 气泡退场后销毁 DOM 与 GSAP timeline；切换 Job 时清理旧序列，避免 memory leak。

## 五、实施分期：先把外观做漂亮，再对接真实事件

### 阶段 A：静态构图与动效原型（前端，0 API 调用）

1. 以用户截图为旧版参考，保留顶部阶段名称和主题文本。先设计一张没有动画也好看的静态构图：主节点、层次化曲线、少量粒子、2–3 个气泡停靠位、清晰的当前状态。
2. 实现 `ProgressEventScene` 的完整气泡生命周期，使用**固定演示事件**推进。主节点移动/演变、轨迹产生、小事件浮现、粒子消散都在同一舞台内连续完成。
3. 制作知识、脚本、动画三种视觉状态，不能三阶段仅换文案。
4. 核对长中文主题、窄桌面、移动端和 reduced-motion；检查鼠标点击、页面滚动、文字重叠。
5. 先交付截图与短录屏，**视觉验收通过再做后端事件接入**。不要因为 JSON 跑通就认为动效美观。

### 阶段 B：正式知识/脚本事件驱动（后端 + 前端）

1. 在 `JobStore` 中增加可选、有界 `display_events`，从现有 `workflow.service` 的**用户安全事件**提取，避免保存 diagnostics。只在有新事件/阶段转换时更新，不产生额外模型请求。
2. 前端按当前 `jobId`、`seq` 增量入队，自动弹出并消散。旧任务缺列表时回退到稳定的 `job.message`。
3. 保留 `script_ready`、失败/中断、项目刷新后恢复、脚本概览和实际 ArtifactRef 判断，视觉不能控制业务完成。
4. 演示页继续使用固定 `sequence`，正式页绝对不能调用模拟事件序列。

### 阶段 C：动画阶段真实事件接线（有条件，可单独 PR）

1. 先直接使用 `AnimationHandoff` 已有 `AnimationPhase`，让视觉主节点跟随动画真实 `queued/running/ready/failed` 状态。
2. 如果需要更有内容的事件气泡，给实际单幕完成或缓存命中补 `animation.scene_ready`；以 `preview_ready` 表示真实资源加载就绪，而非仅模型生成结束。不要增加按秒伪进度。
3. 自然衔接到工作台：进入预览之前，气泡短暂收束到主节点；真实 `preview.ready` 时才出现“可以预览与修改”的按钮。保持脚本已完成后自动续接动画的既有体验。

### 阶段 D：综合验收与收尾

1. 用 Fake JobSnapshot/Event 压测低频、连续、重复、失败、刷新、任务切换、长时间无事件等情形。
2. 检查真实 API 下加载页的内容是否准确：知识阶段确实开始才冒出对应信息，若没有搜索则**不会**出现“正在补充资料”；动画未发布不能出现完成庆祝动画。
3. Playwright 测试两种桌面宽度（建议 1440×900、1280×720）及手机 390×844，重点检查气泡不遮挡状态与按钮、连续循环无跳变、不同浏览器字号与 reduced motion。
4. 视觉回归对比截图和一次录屏；将旧 CSS 中不再使用的 `.bubble-*` 等样式清理，不在正式代码残留两套冲突动画。
5. `STATUS.md` / 前端相关文档只记录确认已完成的事项，不扩展出新的工作流概念或复杂架构。

## 六、验收清单（客观功能 + 主观视觉）

| 检查内容 | 完成标准 |
| --- | --- |
| **真实阶段** | 主进度随知识/脚本 Job 与真实动画 Job 更新，完成、失败、等待语义与后端一致 |
| **事件来源** | 所有带具体行动或成果的气泡均可追溯到真实经过封装的事件；没有发生搜索时不展示搜索成功 |
| **气泡运动** | 从当前节点涌现、沿自然曲线移动、短暂停留、逐渐消散；不是四个气泡固定飘动或持续随机飞出 |
| **视觉重心** | 三阶段有清楚的主节点变化；用户可一眼看出当前阶段，不被粒子与标签淹没 |
| **持续等待** | 长时间没有新消息时仍有安静的环境动效和稳定状态文案，不伪造里程碑或百分比 |
| **失败恢复** | 失败时暂停前进，旧成功阶段仍保持；重试不丢旧作品、不重放旧任务气泡 |
| **刷新恢复** | 恢复正确的当前状态与少量最近进展，不回放全部过期事件，也不重新启动模型调用 |
| **实际可读性** | 气泡文本清楚，移动过程中不晃字；长主题、中文字体及移动端没有裁切或重叠 |
| **减弱动效** | reduced motion 展示静态但有用的状态，其他用户功能与加载结果不受影响 |
| **性能** | 低粒子数量，离屏暂停，组件卸载彻底清理；任务轮询不会被高频重绘拖慢 |
| **页面一致性** | 使用网站当前米白/深绿/暖金设计变量；不要做成突然出现的深色赛博科技特效 |

**明确不通过的形式**：漂亮的气泡动画里不断出现“已经找到 8 个事实”等没有数据来源的内容；每次轮询重复弹出同一事件；字幕重叠、无法阅读；任务已失败但粒子仍在庆祝；真实页面仍只有一个不会动的静态消息；为了动效额外调用 DeepSeek。
