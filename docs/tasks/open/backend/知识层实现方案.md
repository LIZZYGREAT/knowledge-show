# 知识层实现方案

> **任务范围**：将 `docs/work/backend/knowledge/知识层探索与创意策划.md` 的设计落实为可运行的知识层，包含 DeepSeek Flash、Search/Fetch、Research/Creative/Verifier、共享研究状态、正式 `KnowledgePackage` 交付，以及开发者可用的**本地人工检验页面**。
>
> **当前基线**：仓库 `main` 的 `backend/src/knowledge/` 与 `backend/tests/knowledge/` 仍为占位工作区。知识层依赖清单位于 `backend/requirements-knowledge.txt`，本地环境模板为根目录 `.env.example`；现有公共契约位于 `contracts/`。本文是**待执行的实施计划**，不代表代码或真实 API 调用已经完成；不改变脚本层、动画层、正式前端和跨阶段 Schema。

## 一、交付目标及边界

实现完成后，开发者能够在本机打开知识层检验页面，输入例如“Attention”“生日悖论”或者“为什么飞机能够飞行”，可选设定关注方向、知识深度和创作模式，点击开始研究后，获得可读、可检查、可导出的结果：

- 一个或多个**真正有价值的候选方向**：清楚说明值得观看的核心问题、知识收获和可能形成的认知主线；系统给出默认推荐，不强制用户先做专业选择。
- 足以支撑推荐方向的**可靠知识内容**：不是概念名称的堆叠；对关键机制交代为什么、如何发生、哪些条件重要。
- **知识和创意相互推动**：Research 可以直接利用已有知识、推导和必要的外部搜索；Creative 能围绕知识中的对象、状态、因果和变化发现有观看价值的方向，必要时反向提出具体研究缺口。
- **宽松但有效的核验**：Verifier 关注会影响视频正确性的关键事实和误导风险；优先建议局部修订，保留合理创意。
- 正式产物通过当前 `contracts/schemas/knowledge-package.schema.json`，并满足候选引用、知识状态、证据与依赖关系等约束。

产品原则不随技术实现退化：最终创作反对由标题、知识卡片和公式页切换构成的 PPT 式动画。知识层应找到可供脚本继续设计的**知识对象、真实变化、清楚的认知主线**；但本层**不编写分镜、定时字幕、动画代码或最终故事脚本**，也不把想象出的具体视觉形象强塞给下游。

## 三、输入与统一主入口

知识层以已解析的 `ProjectState.brief` 为标准输入，保留用户 `user_input` 和系统 `effective` 的区分。人工检验页可以帮助填写这些字段，但进入主服务后必须使用**同一份标准输入**，不能建立一套只供测试页使用的简化 Prompt。

建议单一服务入口（示意签名，非现存 API）：

```python
async def generate_knowledge_package(
    project_id: str,
    brief: dict,
    *,
    on_event=None,
    run_options=None,
) -> dict:
    """执行知识层研究并返回符合当前公共 Schema 的 KnowledgePackage。"""
```

- `brief` 包含 `revision`、`user_input`、`effective`，需遵守 `ProjectState` 已有字段和可选语义。
- `run_options` **仅供内部调试**，例如 mock/real、允许搜索、最大成本和强制刷新；不进入正式 `KnowledgePackage`。
- `on_event` 接收**面向检验的阶段事件**（开始、完成、异常、阶段摘要及统计），不暴露模型私有推理内容。
- 主函数返回**正式产物**；运行过程和中间状态通过单独 `run_id` 保存，不能把内部 Issue/Source 草稿作为公共字段塞进知识包。
- 正式输出应携带 `project_id`、`artifact_id`、`revision`、`brief_revision` 等已有字段；同一逻辑对象的 ID 在局部修订中保持稳定。

人工检验页的默认输入可以从用户只填 `topic` 开始，使用符合当前 Schema 的项目默认配置填补 `effective`；用户明确填写的模式、知识深度、风格、内容约束不得被覆盖。目标时长读取 `effective.target_duration_ms`；产品典型范围为 150000–180000 ms，**不把知识条目个数或字数绑定到时长**。

## 四、共享 ResearchStore：写入与检索

### 1. 内部对象

内部只保留完成协作所必需的数据，优先让每条数据具有**稳定 ID、所属项目、关联对象、状态与必要正文**。不为通用知识图谱预设额外表和服务。

| 逻辑对象 | 最小信息 | 用在哪里 |
| --- | --- | --- |
| `ResearchTask` | ID、研究问题、发起角色、目的、关联创意/Claim、状态 | 创意缺口、定向补证、研究去重 |
| `Source` | ID、URL/来源、标题、摘要、可选正文引用、获取时间、检索问题 | 保存外部研究依据，避免重复抓取 |
| `Claim` | ID、知识主张、解释、条件、相关概念、获取方式、审核状态 | Research / Creative / Verifier 共享的知识基础 |
| `ClaimEvidence` | Claim ID、Source/推导引用、对应原文或步骤、支持/冲突关系 | 精确核验，避免“有链接就算证据” |
| `CreativeLead` | ID、核心问题、学习收获、知识联系、认知变化、关联 Claim、待确认疑问 | 保留创意价值并提出研究需求 |
| `Issue` | ID、对象引用、关键问题、建议处理、处理角色、解决状态 | 宽松而可追踪的局部修订 |
| `Run` / `RunEvent` | 运行 ID、输入摘要、阶段、时间、调用结果与失败信息 | 人工检验与问题定位 |

知识来源 `provenance` 至少区分 `model_generated`、`external_source`、`derivation`、`user_material`，这只是内部来源记录。模型直接给出的内容可以写入 `Claim`，状态应先是待核验；若无法获得适当依据，不能仅凭模型自述将它标记成 `verified`。

### 2. 保存规则

- 一份 Source 可支持多条 Claim，一条 Claim 可关联多个 Source；按 URL 规范化和内容特征去重，但**不同条件下成立的主张不得粗暴合并**。
- 原始 Fetch 内容应有保存位置；ClaimEvidence 要能定位相关片段或公式，不只保存来源首页。
- Claim、CreativeLead、Task 都要带 `project_id`，不同项目默认隔离；本项目中的已用事实可复用，但不得未经判断自动混入其他主题。
- `rejected` 或已解决的问题可留在内部，帮助避免重复错误；普通 Agent 检索默认隐藏废弃记录。
- API Key、模型内部推理、无意义的大段请求历史不进入 ResearchStore 或导出报告。外部网页作为资料，不具有向 Agent 下达指令的权限。

### 3. 内部知识检索流程

采用**先内部、再外部**的策略：

```text
Agent 提出具体知识需求
  → 关键词、术语别名、ID、类型与审核状态召回 Claim
  → 根据 depends_on / 证据关联补充必要上下文
  → 返回紧凑结果（内容、条件、状态、来源 ID）
  → 仍有明确缺口：新建或复用 ResearchTask
  → Research 根据需要直接推导或调用 Search/Fetch
  → 新证据和 Claim 入库，重新供各角色检索
```

初期不需要 embedding。检索接口可围绕 `search_claims(question, filters)`、`get_claim_and_evidence(id)`、`get_related_claims(id)`、`list_open_tasks(project_id)` 等能力组织。**返回结果是否回答了当前问题**比检索算法是否先进更重要。注意支持中英文术语和关键别名，例如 Attention / 注意力机制。

## 五、Research 与 Creative 的真实交互

### 1. Research 的三个知识来源

Research 先结合 Brief 与已有知识判断需求，然后按问题性质选择：

1. **直接使用 Flash 已有知识**：生成基础概念、常见机制、知识关联及合理解释，写入待核验 Claim。
2. **可复核推导或计算**：写清关键关系、条件和中间步骤；必要时利用普通 Python 计算核对。
3. **DeepSeek Search/Fetch**：针对时效性事实、具体数值、争议、重要出处、尚未解决的知识缺口进行定向搜索；只抓取值得阅读的正文。

搜索不能变成默认流水线，也不能凭空捏造来源。Search 只给线索；Claim 由原文、推导和可复核信息支撑后才能获得正式核验状态。搜索结果可以使用官方 `summary`、`rerank_score`、`authority` 辅助选择阅读对象，但这些字段本身不能代表事实已经成立。

### 2. Creative 的核心任务

Creative 使用 ResearchStore 中的事实、现象、动态关系和待确认假设，形成**值得观看的知识方向**。它应考察：观众会持续关注什么真实知识对象或关系；状态为何变化；上一阶段如何推动下一阶段；最终发生什么认知转变；这些变化是否对故事、实验或解释有实际作用。

禁止把创意生成简化为“固定生成三个故事模板”或“给五个知识点分别配一个画面”。Creative 可以内部大胆探索，但输出给知识层的候选不能提前固定分镜、角色造型、镜头和动画技术。

Creative 需要进一步研究时，生成一个有明确目的的 `ResearchTask`：**研究问题 + 为什么影响当前创意 + 现有 Claim 引用 + 希望消除的知识缺口**。Research 先检索已有数据，再选择模型知识、推导或外部查询；回答允许为“成立、有条件成立、不支持、尚不确定”，不能只寻找支持创意的证据。

Research 发现有价值的因果关系或反直觉现象，也可以产生简短的发现线索并关联 Claim，供 Creative 再次检索。**不要求两者循环固定次数**；确有关键缺口再执行补充。

## 六、Verifier：关键风险检查与最小修订

Verifier 对创作和知识形成**两次自然检查**：候选基本成立后，检查其核心知识规则是否明显错误；发布前，检查被正式方向引用的关键事实、条件、计算与容易误导的简化描述。可以将两次审核封装为同一模块的不同调用方式。

| 内容 | 建议核验强度 | 遇到问题时的行为 |
| --- | --- | --- |
| 基础常见概念 | 轻量独立检查，必要时查已有依据 | 局部修正解释 |
| 数学/计算机制 | 核对关键步骤、维度和前提 | 修正推导或条件 |
| 实验、统计、历史、时效事实 | 优先核对可追溯资料 | 补证、改写或暂不采用 |
| 支撑大胆创意的反直觉结论 | 检查核心因果、适用条件及反例 | 优先保留创意核心并限定成立条件 |
| 隐喻可能造成的知识误导 | 检查观众可能获得的错误理解 | 反馈知识性限制，不决定具体美术 |

内部审核结果使用 `pass / revise / block` 的轻量结果即可，另记录相关 Claim、问题和建议；无需长篇审稿报告或机械多来源评分。`block` 只针对**当前关键知识不能按原样使用**，不代表整个视频必须失败。普通文案差异不应触发重研究；改变过的 Claim 再局部核验即可。

注意：当前对外契约 `knowledge_units[].verification_status` 为 `verified / needs_review`，与内部 `pass / revise / block` **不是同一字段**。发布时必须显式映射、检查证据和引用；不能将 `pass` 直接写到公共状态字段。

## 七、候选收敛与 KnowledgePackage 交付

先判断是否已有**值得制作的方向、足够支撑该方向的知识、无阻碍交付的关键事实错误**。达到后即结束；不为凑条数、搜索轮次或候选数继续扩充。推荐方向优先深化，其余有真正差异的可行方向保留足够的核心说明与可靠基础知识，用户改选后再针对缺口补充。

正式组装必须对齐当前仓库字段：

| 公共位置 | 组装要求 |
| --- | --- |
| `directions[]` | 至少一个候选；真实填写 `id / title / core_question / hook / learning_goal / knowledge_refs`，保留知识驱动的吸引点 |
| `directions[].duration_fit` | **必填** `status / reason`；状态为 `adequate / thin / dense / uncertain`，按 `effective.target_duration_ms` 判断，不强制一律 adequate |
| `directions[].visual_potential` | 可选；说明可观察的知识关系、状态或因果变化，不能只写“画面丰富”，也不应规定具体视觉对象造型 |
| `recommended_direction_id` | 指向实际候选中优先推荐的一个；推荐依据包含用户需求、认知主线和创作价值 |
| `knowledge_units[]` | 正确区分 `content / explanation / importance / conditions / depends_on / verification_status / evidence_refs`；知识单元数量由主题决定 |
| `evidence[]` | 使用契约支持的 `external_source / mathematical_derivation / user_material`；外部资料有 `locator`，数学推导有可复核 `details` |
| `constraints` | `required_knowledge_refs` 只放确实不能省略的知识；`must_not_misrepresent` 记录容易被错误表达的关键条件 |

**现有契约特别注意**：`verified` 知识必须有至少一项 `evidence_refs`；候选 `knowledge_refs` 只能指向 `verified`；`needs_review` 可作为尚待处理线索留在知识包中，但不得被候选或后续脚本作为已核验事实引用。为减轻下游负担，通常把无关的待审核草稿留在内部 ResearchStore。

对实际新生成的知识包，先运行 `Draft202012Validator` 对应 Schema 检查，再在本层检查：候选引用存在、不能引用未核实知识、证据引用存在、推荐 ID 存在、依赖无环以及必须知识约束合法。仓库原有 `contracts/validate_contracts.py` 目前使用**五类连贯 Mock 一起做全链检查**，不能直接拿仅有的一个新 `KnowledgePackage` 当作全链测试输入；须区分本层新输出验证与仓库附带的 Mock 验证。

交付时做一次简短的**创意意图保留检查**：只看候选描述和关联知识，脚本层是否能理解“为什么值得看、什么知识关系会产生变化、观众能理解什么”。不需要新增专门审核 Agent，也不以长论文式说明填满这些字段。

## 八、本地人工检验页面：必须交付的第一批功能

本部分是本次开发的**核心验收入口**。只给一个后端 JSON 或打印日志不足以完成这项任务。

### 1. 页面最小布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 知识层人工检验 · 本地开发入口                               │
├───────────────────┬──────────────────────────────────────────┤
│ 输入              │ 运行状态与本次结果                        │
│ 主题 *            │ 阶段：研究 → 创意 → 核验 → 交付           │
│ 具体方向（可选）  │ 当前动作、用时、搜索/抓取次数             │
│ 创作模式（可选）  │                                          │
│ 知识深度（可选）  │ 推荐方向：核心问题/看点/学习收获           │
│ 个人创意（可选）  │ 其他候选：可展开比较                      │
│ 包含/避免（可选） │                                          │
│                   │ 选项卡：                                 │
│ [开始研究]        │ [候选] [知识] [证据] [问题] [运行记录]     │
│ [重新运行]        │                                          │
│                   │ [人工评价/备注] [下载 JSON 与运行记录]    │

```

实现时可用 Streamlit 表单、状态组件、选项卡和 JSON 下载功能，尽量做到**先看到有价值的作品方向，再按需展开技术细节**。不需要做成复杂工作台。

### 2. 使用体验和行为

- **输入**：仅主题必填。`focus / creative_mode / knowledge_depth / creative_idea / must_include / must_avoid` 可以选填。未选则遵循项目有效默认设置；输入作为本次真实 Brief 保存。
- **开始研究**：显示任务已开始与当前阶段；每当完成一次 Research、Creative、Verifier 或 Search/Fetch 动作，更新事件摘要。避免只显示一个漫长的加载动画。
- **结果摘要**：最显眼的位置显示**推荐方向**及其 `core_question / hook / learning_goal / recommendation_reason / duration_fit`；其他候选可展开查看。不要一进页面先丢给用户巨大的 JSON。
- **知识查看**：按候选或知识状态筛选 `knowledge_units`；每条可以展开 `content / explanation / conditions / depends_on`，显示其验证状态和证据引用。
- **来源核验**：点击证据可查看对应资料标题、URL、可复核推导或来源片段。对 model-generated Claim 显示“来自模型初稿、后续如何核验”，不得显示不存在的网页来源。
- **问题查看**：显示 Verifier 真正指出的少数关键风险与最小修正结果；如果没有问题，可明确显示“未发现阻碍发布的关键问题”，不要生成空泛审稿报告。
- **运行记录**：显示每阶段开始/结束时间、调用次数、Search/Fetch 关键词、错误和必要的调用用量；不展示、存储或导出模型内部私有推理。
- **人工检验记录**：允许开发者在本次运行上选择“可继续使用 / 需要调整 / 当前不可用”，填写一段自由备注并保存到本地 Run 记录；这些是人工评价，不会自动把错误知识改为 `verified`。第一次实现不必提供复杂评分表。
- **结果导出**：成功时下载符合契约的 KnowledgePackage JSON；另外可下载本次输入、人工备注和摘要日志，方便人工复核或提交问题。保留最近的运行记录，重新运行不覆盖此前结果。
- **失败状态**：API 不可用、来源抓取失败、核验缺依据、Schema 不通过时，显示具体阶段和原因，并可查看已有候选或部分研究材料；**不能伪造已成功的知识包**。必要时允许先只查看草稿。

### 3. Mock 与真实模式

人工检验页应共用真实服务入口，并支持**离线 Mock 模式**。Mock 使用固定的研究资料和模拟模型响应，确保无 API Key 时也能检查页面、数据连接和失败展示。真实模式才调用 DeepSeek。

两种模式的页面布局、运行结果对象和 Schema 验证逻辑保持一致。界面必须醒目标出 `Mock` 或 `Real API`，避免将模拟结果当成模型效果。人工检验重点仍是真实 API 结果；Mock 只用于工程自检。

### 4. 可复现的手工验收

开发者可输入任意主题，不应被下面的示例题目写死。完成后至少亲自手动检查下列情形：

| 操作 | 应观察到的实际结果 |
| --- | --- |
| 只输入“生日悖论”并开始 | 出现可理解的推荐方向、核心知识和解释；能查看依据，KnowledgePackage 校验通过 |
| 输入“Attention”，设置 `advanced` | 方向与知识深度合理，涉及的计算机制和限制有解释，不只是罗列术语 |
| 输入宽泛主题“物理”，设置创意优先 | 系统尝试寻找有区别的知识切入点，推荐理由具体，不直接生成一堆常规 PPT 页面规划 |
| 使用相同主题改成直观演示 | 候选侧重点与视觉变化依据会合理调整，同时仍保持知识可靠 |
| 输入自定义具体方向与必须包含项 | 不擅自换题，交付结果对用户显式要求有清楚响应 |
| 查看任意已核实知识的证据 | 能打开真实来源定位或阅读可复核推导，不存在伪造引用 |
| 断网、API Key 缺失或 Search/Fetch 出错 | 页面显示真实错误和部分进度，不把失败视为完整成功 |
| 使用离线 Mock | 无密钥也能完成页面展示和结构校验，并明确标记 Mock |
| 下载生成 JSON | 直接通过本层 Schema 与引用一致性检查；必要字段完整，包括 `duration_fit` |

不需要为了验收再设计复杂的 A/B 对照实验、定量评分平台或固定知识条目数。**人工首先判断这个主题是否真的产生了值得制作、能形成视觉主线的方向**，其次检查事实依据和工程链路。

## 九、实现顺序与验收检查点

建议按可独立运行的小增量推进，避免把所有 Agent、数据库和页面一次性堆出来，最后才发现无法使用。

| 阶段 | 主要工作 | 可以立即验证什么 |
| --- | --- | --- |
| 1. 契约适配与入口 | 建立主函数、Brief 解析、公共 Schema 验证、Mock 数据入口 | 调用一次离线研究能返回合法知识包；校验能识别无效引用 |
| 2. 本地人工检验页 | 表单、候选展示、知识/证据/问题标签页、JSON 下载 | 打开浏览器输入任意主题；先用 Mock 检查全部浏览与错误展示 |
| 3. DeepSeek 接入 | Flash Responses、Search、Fetch、环境变量与异常处理 | 手工输入主题可以完成一轮真实研究；日志显示哪些资料确实被读取 |
| 4. 共享研究与内部检索 | ResearchStore、Claim / 证据关系、按任务检索与局部补充 | 相同已知信息可复用；Creative 的研究缺口能找到对应 Claim |
| 5. 创意与核验闭环 | Research ⇄ Creative、Verifier、推荐方向优先深化 | 输出能体现主线和知识变化；关键错误可局部修改；不陷入固定循环 |
| 6. 收敛与完整验收 | 生成完整 KnowledgePackage、引用检查、真实主题手动检验 | 页面、实际 JSON、知识事实和创意质量可以同时检查 |

关键要求：**第 2 阶段的页面不能只绑定 Mock**。完成第 3 阶段后应立即对接真实主入口，让人工尽早发现 Research 查询无价值、Creative 输出套路化或 Verifier 过度否决的情况；这些属于产品质量缺陷，不能仅凭测试通过宣称已完成。

### 必要的工程测试

- `pytest` 覆盖内部检索、知识关系、相同来源去重、问题状态、运行事件及主要失败路径；使用 Mock，不依赖实时外网。
- 对公开知识包使用仓库现有 Schema 进行真实对象验证，单独测试知识包的候选、证据、依赖关系；不能只运行仓库原有五份 Mock 而声称新生成数据已验证。
- 运行仓库现有 `python contracts/validate_contracts.py`，确保没有破坏公共 Mock 和契约。
- 页面人工操作完成一次真实 API 的端到端流程；记录实际输出文件、是否通过检查、遇到的主要问题和运行耗时。
- 每完成一个稳定增量按仓库 `docs/work/workflow.md` 及时 Commit；不要擅自改动其他成员工作区或共享契约。

## 十、完成标准与交接

本任务完成不以“建好了三种 Agent 类”“能调用 API”“能生成 JSON”作为唯一依据。至少要同时满足：

1. **开发者能够独立使用人工检验入口**，输入任意主题和可选创作偏好，看到完整且可理解的真实运行结果。
2. 能追查关键知识从模型、推导或外部资料中如何获得，以及对应的核验结果；外部搜索是按需执行、可见且可复用的。
3. 推荐方向有具体核心问题、清楚的认知收获和真实知识关系，具有为下游设计**明确视觉对象、连续变化和贯穿主线**提供素材的可能性，不能退化为知识大纲与 PPT 页建议。
4. Verifier 能识别明显的关键事实问题，并尽可能局部修正；普通差异和可接受的艺术构想不会被机械阻断。
5. 输出符合当前知识包 Schema，候选只引用已核实知识，证据和依赖引用真实可追踪。
6. API 调用失败或知识缺口尚未解决时有清楚的状态，既保留可用中间结果，也不伪报正式交付成功。

具体实施经验可补充到本目录的实现文档或测试报告中。产品理念、跨层契约与本方案各自承担不同职责；无需为了这次实现重复制造另一套接口定义。
