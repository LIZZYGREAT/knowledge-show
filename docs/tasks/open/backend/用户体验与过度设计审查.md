## 一、评价基准与总判断

产品面向普通创作者，用户只需要提出想法、观察成片、表达修改、下载。知识来源、验证状态、产物版本、场景 ID、Agent 分工是系统内部的可靠性设施，不应变成用户义务。优先关注：实际视频是否可理解、视觉表达是否有吸引力、少操作、低费用、错误可恢复。必要的事实核验与运行安全仍应保留。

本轮相对上一版取得重要进展：PR #16 将知识→脚本→动画→真实工作台→局部动画修订→MP4 导出的实现纳入 `main`。仓库 `STATUS.md` 记载 120 个后端测试、14 个前端逻辑测试、32 个浏览器 E2E 通过；PN 固定样本七幕 165 秒、3960 帧 H.264 导出成功。这些是仓库记录，不等于对任意主题通用效果的证明。**新主题真实模型脚本、动画生成及反复修订的质量还没有完成付费实测。**

当前不需要推翻已有 ResearchStore、五类公共 Schema、ArtifactRef/版本机制、Player/工作台。它们能保护结果正确性。真正需要优先处理的是限制生成灵活性的规则、被拆成多步的创作流程、隐形的失败成本，以及把技术操作留给用户的体验。

## 三、必须优先处理的问题（P0）

### 1. 没有旁白，却按配音视频限制字幕比例

定位：`backend/src/script/prompts/script_writer.md` 第四节，“字幕占屏时间争取不超过四成”“每个场景至少留一段完全没有字幕”。当前产品明确没有配音与音效。无声知识视频对对象名、关键条件、因果和结论往往需要可读文字。统一的 40% 比例会系统性减少有效解释。

**修改**：取消固定字幕占比与逐场景强制无字幕段；替换为“字幕用于补足画面无法独立表达的关键信息，优先清晰、简洁、不遮挡重要对象；文字密度随主题、对象可读性和有无配音动态决定”。继续保留对象首次出现须能识别、字幕起止时间准确、不能挡住重点。**无需新增字幕审查 Agent。**

**验收**：选择一个无旁白的复杂技术主题，静音播放后观众能知道对象是什么、如何变化、得到什么结论；不以字幕占比是否少于 40% 作为通过标准。

### 2. 动画生成对上游知识与全片关系掌握不足

定位：`backend/src/animation/service.py::generate()` 将每个场景分别送入 `direct_scene(client, scene, profile)`；`backend/src/animation/director.py::direct_scene()` 模型数据仅有 `scene/style_profile/previous_resource/feedback`。脚本场景虽含知识引用和视觉注释，却未传该引用对应的真实知识条目、条件和全片前后场景关系。当前动画生产也没有显式使用知识层的 KnowledgePackage 内容。

**影响**：单幕可画、全片却不连贯；对象身份变化、关键知识机制误表述、风格与叙事节奏割裂。浏览器几何/时间校验不能发现这种语义问题。

**修改**：在动画服务层装配轻量内部 `SceneContext`（不新增公共 Schema）：当前场景与全片 `core_message`、前后场景的核心目标、选中 `knowledge_refs` 对应的 verified 内容和 `conditions`、跨幕稳定的可复用关键对象/已完成场景简述。上下文与模型输入保持精简，不复制整个 ResearchStore、不追加新的证据审核轮次。模型继续只返回受控动画资源，不能改写上游事实。

**验收**：两幕之间同一知识对象身份连续；让场景模型在无额外研究 API 调用下拿到其真正需要的事实与前提；不同主题都能保留核心知识表达。

### 3. 创作启动分成知识脚本与动画两步，进度状态不统一

定位：`frontend/src/features/progress/AnimationHandoff.tsx` 独立“开始制作动画”按钮；`frontend/src/features/progress/TaskProgress.tsx` 顶部动画阶段一直按主脚本 Job 的 `script_ready` 展示“等待动画制作”，下方另用动画任务状态。

**影响**：用户误以为需要理解和推进内部工作阶段；动画运行或完成时进度线可能仍说“等待”。

**修改**：首次“确认开始制作”时清楚说明会运行研究、脚本、动画及可能的费用，用户确认后默认连续执行直到预览就绪。若选择“先看脚本”才停在中间。短期内可保留后端两个任务接口，由前端协调器在脚本 `script_ready` 后启动动画；启动之前检查相同项目是否已有匹配的动画/正在运行的任务，避免重复扣费。前端聚合两个 Job/Preview 的状态，形成一条真实三阶段进度线。对当前 Key 已不可用的情况提供明确重连操作；不自动偷偷重试付费调用。

**验收**：一次确认→真实知识→真实脚本→真实动画→可播放预览；刷新不重复计费；动画在制作时显示“正在制作”，完成时显示“可预览”。

### 4. 多幕动画失败会浪费已成功的模型调用

定位：`backend/src/animation/service.py::generate()` 对 `script.scenes` 逐幕执行 `direct_scene`，在全部结果返回后才发布；对模型输出无有限局部格式修复，也未持久保存未发布但已校验的单幕结果。

**影响**：后几幕因结构格式失败可能需要从第一幕重新生成，成本和等待都增加；模型一次输出必须满足严格 keyframes/文字/颜色/路径条件，失败概率由后续实测判断。

**修改**：单幕合法结果写入私有临时任务目录（按项目、脚本 ArtifactRef、风格和场景输入摘要定位），失败则只对失败幕进行一次受控修正/重新生成；重新启动时复用未变化的已成功单幕。全部生成、校验与渲染成功后一次性发布新 Manifest；临时成果不可作为用户当前成片，也不可覆盖已发布版本。保留总调用次数、超时、费用边界；不新增分布式队列。

**验收**：模拟第七幕失败，首次任务不发布，重试无需重复前六幕模型调用；旧可播放版本保持不变。

## 四、产品体验及创作自由问题（P1）

### 5. 通用动画表达能力被四类基本几何对象限制

定位：`backend/src/animation/director.py::validate_program()` 强制 2–60 个对象、每对象 2–64 个关键帧，形状仅 `circle/rect/path/text`；`frontend/src/animation/runtime/VectorScene.ts` 仅插值 `x/y/opacity/scale/rotation`。通用渲染对 Profile 的材质、光影等高层信息没有丰富的运行时表达。

**处理边界**：保留数值有效、无可执行代码、路径安全、ID 稳定等必要安全门槛。取消“至少 2 对象”这类缺乏教学意义的数量约束，允许静态/单对象场景。不一次性放开任意 JS/HTML；先用真实新主题找出需要的受控形态，按需增加 SVG 分组/路径变形/描边/渐变/图层关系/明确物理对象动态行为等。风格不能只换背景和颜色，要由真实材质和构图表现。绝不强制各幕套同一视觉模板。

**验收**：对比科普机制、概率直观演示、非理工叙事三个主题；同一美术风格下也能设计不同视觉对象，而非所有视频都是矩形、圆形平移。

### 6. “自动美术风格”实际默认精密科学

定位：`backend/src/animation/director.py::resolve_profile()` 和 `frontend/src/animation/styles/resolveStyle.ts` 对 `auto` 均转为 `precision-science`；仅用户填写特定美术自由文字时后端尝试另外生成 Profile。

**修改**：根据脚本题材与用户明确偏好自动选择合适的一份既有 Profile，默认逻辑可通过模型已生成的脚本元数据进行简单判断，避免为选风格单独多开一次模型调用。用户没填美术偏好时不应该所有主题默认科技风。用户明确风格时优先尊重。

### 7. 修订语义依赖关键词，未选择元件时难以直接提全局修改

定位：`backend/src/animation/service.py::revise()` 以正则判断“反转”“改方向”“时长”等为上游；当 `scope=unknown` 且 anchors 为空时，`affected` 为空后报“请先选择…”；`frontend/src/features/revision/Workbench.ts::requestFor()` 未选择时构造 unknown。

**修改**：选择元件时优先精确定位；没有选择时支持“当前画面/整片”范围（在表达模糊时仅询问一次）。短期可提供一个默认的“整体风格/节奏”修改目标，而非强制用户手动选择；关键词仅作为提示，不应直接把“镜头反转”认成知识事实修改。仍尊重真实上游知识内容，确需改脚本时清楚引导和保留反馈。

### 8. 工作台每次模型修改需重填 API Key

定位：`frontend/src/features/revision/editor-layout.html` 独立模型密钥输入；`frontend/src/features/revision/Workbench.ts::submit()` 结束时清空。

**修改**：会话内临时保留 Key，不写 URL/localStorage/产物；只有真正触发模型调用时才使用；无须模型的固定场景小调整不索要 Key。若正式 React 入口/工作台能共享安全的会话内连接则复用，不必为了临时黑客松项目引入完整用户账号系统。

### 9. 修改创作偏好可能触发整个新项目及重复研究

定位：`frontend/src/App.tsx::submit()` 以完整 `sameUserInput` 判断，任一字段差异时新建项目。对新增 focus 或重要知识要求，新项目可以合理；仅修改艺术风格却重新知识研究，费用不合理。

**修改**：优先把纯视觉偏好变更路由到现有动画风格版本；内容主线变化时使用新脚本或必要的知识修订。暂不建设复杂差异依赖图；只先区分“内容变化”和“纯美术变化”。返回创作页不应轻易丢失当前项目入口，另设“开始新作品”。

### 10. 关键知识门槛中空 required 被扩大为所有引用知识

定位：`backend/src/knowledge/creative.py` 允许 `required_claim_indices` 默认空；`knowledge/service.py`、`knowledge/verifier.py` 和 `knowledge/package.py` 在多处用 `candidate.required_claim_indices or candidate.claim_indices`。当模型没给或给空时，所有参考 Claim 变成“必须全部通过”，容易让一个可以舍弃的可选细节拖垮整个方向。

**修改**：先区分“未填写必要列表”和“明确必要列表为空”的语义；生成时必要列表应只覆盖真正决定核心讲述的事实。遇到不可靠的非核心知识时允许删掉并保留方向；真正核心事实不成立时仍应阻止错误成片。优先利用现有 `minor_or_optional` 类型，不增加新的全流程复审。增加一条可选 Claim 被拒但方向可交付的测试。

## 五、还没实现或只在固定样本验证的内容

| 通用新主题全流程质量 | 模型客户端和受控资源已有，固定 PN 样片经过实际播放/导出；新主题真实模型验收尚缺 | 小样本实测不同题材，至少一条从用户主题到 MP4 的真实付费验收，记录实际费用、失败原因与观看效果 |

## 六、应保留的工程约束

**保留**：关键事实校验、低风险基础知识 `internal_review`、风险高才补外部证据、公共 Schema、严格版本引用、任务失败后保留旧成果、密钥不落盘、脚本/动画时间正确、稳定元件 ID、画面与输出分离、模型输出不执行任意 JS、实际浏览器可加载才发布动画。这些会直接保护用户体验和数据安全。

**放松**：无配音的强制少字幕、没有解释价值的对象/关键帧最低数量、所有候选引用知识自动升级为必要、仅凭关键词硬路由、每幕孤立生成、不保留中间成果、不明确通知就重复调用模型的工作流。

**不要新增**：研究评分仪表盘、普通用户可见的证据来源审批、必须手动审阅每条 Claim、每阶段都要人工确认、另起微服务/任务队列、单独的“审美验证 Agent”来替代实际观看、固定视觉模板流水线。

## 七、最小实施顺序与验收

1. **先修真实使用障碍**：字幕规则、统一进度和一次确认后连续生成、凭证在工作台的使用方式。完成后用 Mock 验证，无在线费用。
2. **再修高成本失败**：单幕临时缓存和一次有界格式修复、跨幕知识上下文与稳定对象，使用 2–3 场景的模拟失败回归。
3. **基于小样本解除创造性限制**：三个不同类型主题先用固定/注入客户端验证流程，再经确认仅做一条真实新主题视频，观察实际画面、等待时长、调用次数和修订成功率。按真实问题扩大安全矢量语法，而非事先实现一个完整动画编程语言。
4. **最后补友好修订及文档**：无选择时可反馈、合理分流上游修改、艺术偏好不重跑研究、更新当前 main 状态；不把暂未实现的语义修订宣称已完成。

### 建议的回归用例

| 验证场景 | 预期结果 |
| --- | --- |
| 用户只填主题并点击一次“开始制作” | 系统自动运行到预览，可查看真实阶段；没有重复付费调用 |
| 脚本已完成，动画生成中 | 顶部进度显示真实动画正在制作，而非永远“等待” |
| 第三幕模型格式错误 | 一次有限修复；失败重试复用前两幕合法成果 |
| 用户说“让镜头转过来” | 优先视作视觉动作反馈，不因“方向”误路由到知识层 |
| 用户不选对象说“整体更轻快” | 可以提交全局反馈，或出现简单的范围确认，不以内部 ID 或“必须选 clip”阻止 |
| 用户更换纸艺风格 | 不重新研究知识；没有反复要求填写同一会话 Key |
| 基础事实正确但旁枝引述存疑 | 可删除该枝节，核心讲述继续；错误核心事实仍必须阻止 |
| 无配音技术视频 | 对象身份、因果和结论可从画面与必要字幕理解，不卡固定 40% |
| 任意新主题 | 不复用 PN 固定样本冒充真实生成；通过实际渲染与引用校验之后才显示预览 |

## 八、执行边界与交付

在新任务分支实施，先阅读 `AGENTS.md`、`contracts/`、`docs/work/design-principles.md` 与对应代码，按小的可独立验收增量提交。改动公共 Schema 和双方模块边界时先同步协商。本轮重点是让现有链路**更少让用户做事、更能容纳不同主题、失败更少浪费钱**。完成报告逐项标明实际测试结果、修改文件和剩余能力；不凭旧 PN 固定样片证明新主题的完成度。
