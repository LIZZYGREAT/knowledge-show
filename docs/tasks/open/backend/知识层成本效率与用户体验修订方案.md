# 知识层成本效率与用户体验修订方案

> **审查基线**：`feat/knowledge-layer-implementation`，提交 `2236afc8`。任务面向 `backend/src/knowledge/` 的既有实现及本地人工检验页，目标是把首版可运行工作流进一步调整为**普通人真正愿意使用的知识视频制作能力**。
>
> **本次只修订知识层的运行策略、结果呈现和局部接口适配**，不要求重新设计 Agent 架构，不代替脚本/动画层开发，也不把开发者检验工具变成正式前端。涉及 `contracts/` 的语义调整须先与共享接口负责人确认，再同步 Schema、示例、校验和消费方。

## 一、现状与问题定位

现有分支已经实现 Research、Creative、Verifier、Search/Fetch、ResearchStore、KnowledgePackage 和 Streamlit 人工检验页面，工程基础应予保留。此次修订的目标不是继续堆模块，而是解决两类实际的产品问题。

**一是审核与研究过严，可能增加金钱、耗时与内容损失。** `verifier.py` 当前要求被采用的 Claim 必须具有标记为 `supports` 的来源或推导；没有该依据的常见正确知识会转入 `needs_review`。`service.py` 随后可能多次调用 Creative、Verifier 改写方向，却未必主动补齐真正有风险的知识；这会造成重复调用、优质内容被删和生成失败。`research.py` 还应更明确区分“已有知识足够”与“确实需要外部检索”。

**二是内部运行信息与使用者可理解的内容尚未清晰分层。** `devtools/review_app.py` 目前展示 Agent 阶段、搜索次数、证据 ID、错误内容等，适合研发排查，却不适合直接复用为普通用户界面。普通创作者关心的是选题方向、看点、知识是否值得讲以及下一步能做什么，不应被 API、令牌、调用失败、Traceback、原始模型状态等工程信息打断。

这两类问题共同遵循一个取舍：**以足够可靠、足够有趣、足够顺畅为目标；内部判断为产品服务，不能让用户为系统的研究流程付出不必要的时间与成本。**

## 二、总体修订原则

1. **不强制逐条外部举证。** 模型已有的稳定、低争议基础知识，可以先直接写入共享知识库，在轻量核查后使用；只有确实需要外部依据的事实才 Search/Fetch。
2. **风险决定核验投入。** 优先核验会改变核心结论的事实错误、关键计算、重要因果、具体数值、新近或争议事实、可能误导的简化。不让 Verifier 因普通措辞或非关键细节反复打断。
3. **默认一次足够好的生产过程。** Research、Creative、Verifier 正常完成后即可收敛。补充搜索、再次生成或再次核验必须有具体可修正的缺口；不为凑资料或提高形式上的完备度循环。
4. **先保留知识和创意，再做最小修正。** 缺少外部出处不等于知识错误；候选中可选的一条素材未确认，不应导致整个方向被重写或丢弃。
5. **正式用户界面和研发诊断界面分离。** 用户只看经过产品语义加工的阶段、结果、反馈和必要操作；原始 API / Agent / 数据库信息只进入内部日志和明确的开发者诊断区。
6. **节约成本但不伪造正确性。** 缓存可复用的材料，减少重复调用；对于不能可靠判断的高风险事实，选择补充核验、调整表述或暂不使用。禁止将模型自信、无关网页或虚构推导包装成证据。

## 三、核验策略：从“证据门槛”改为“必要的质量检查”

### 1. 区分知识风险与处理路径

| 情况 | 处理 | 是否默认联网 |
|---|---|---|
| 常见概念、稳定定义、低争议基础机制 | Flash 直接产生，Verifier 在同一次集中审核中检查明显错误、矛盾与关键条件 | 否 |
| 容易用计算或推导复核的知识 | 保存真实、可复核的关键计算步骤；必要时进行确定性计算 | 否 |
| 具体数字、实验、历史事件、时效性事实、争议结论 | 优先利用已有可靠资料；缺口确实重要时再定向 Search/Fetch | 视情况 |
| 创意的核心反直觉机制 | 检查实际成立条件、是否存在明显反例、是否会误导观看者 | 视风险 |
| 对主线无影响的可选材料 | 能确认则使用；不能确认就删去或弱化，避免拖慢整条视频 | 通常否 |

这不是要求程序给每个 Claim 打复杂风险分数。可由一个轻量判断决定“可直接复核 / 需要进一步依据 / 暂不能使用”。同一 Verifier 调用尽量同时覆盖所选方向的关键 Claim，避免为每条基础知识单独发起模型请求。

### 2. 对现行证据契约的最小调整（需共享接口确认）

目前 `contracts/schemas/knowledge-package.schema.json` 要求 `verified` 条目至少有一个 `evidence_refs`，而 `evidence.kind` 仅允许 `external_source / mathematical_derivation / user_material`。因此，**仅修改 Verifier Prompt 无法让“经过内部轻量核查的基础知识”合法交付**。

推荐与队友确认一次最小扩展：

- 在 `evidence.kind` 中新增 **`internal_review`**（名称可在协商时确定），其 `details` 记录简短的核查依据或适用条件；无需 `locator`，不声称拥有外部出处。
- 仅用于稳定、低争议、低风险的常识性知识。`internal_review` 明确表示内部质量复核记录，**不是独立外部证明**。涉及具体实验、时效性数字、争议或核心高风险结论，仍须使用实际外部资料、有效推导或移除不确定主张。
- 保留 `verified` 必须有 `evidence_refs` 的现行约束，不用假装数学推导、不借无关网页凑引用。内部复核记录可以轻量生成，不触发新搜索。
- 同步更新 `contracts/接口契约与协作规范.md`、Schema、Mock、`contracts/validate_contracts.py`、本层 `package.py`、测试及下游消费方对 evidence 类型的处理。**确认前不在共享契约中单方面加入新值。**

若当日无法协调共享契约，先做不涉及 Schema 的改进：复用现有真实资料和实际推导、减少重复搜索，并在人工检验中明确显示“基础知识暂无可交付的依据类型”。不要用错误类型冒充有效 evidence；此临时方案仍会限制纯模型基础概念的正式交付，需记录为待协调问题。

### 3. Verifier 返回更有用的处理原因

内部区分三种需要不同处理的情况：

- `fact_problem`：核心事实、计算或因果关系有错误 → 交给 Research 或 Creative 做局部修正。
- `needs_evidence`：主张可能成立，但属于必须补证的高风险知识且当前依据不足 → 优先检查缓存，必要时定向检索一次。
- `minor_or_optional`：表达细节或非关键可选材料有问题 → 修正、弱化或省略，不影响主方向继续。

正式核验结果仍可映射为现有 `pass / revise / block`；细化原因留在内部 Issue，不需要增加独立审核 Agent。不要将“没有外部链接”自动映射为 `block`。

### 4. 调整 service.py 的恢复策略

当前 `Creative → Verifier → Creative → Verifier → ...` 的恢复不应成为常规路径。建议按以下优先级处理：

```text
研究与创意形成候选
    ↓
一次集中风险核验
    ├─ 关键知识通过 → 直接组装并交付
    ├─ 基础知识可轻量确认 → 内部复核记录，继续组装
    ├─ 高风险核心知识证据不足 → 从缓存补证；必要时一次定向检索
    ├─ 局部事实或表达有误 → 只改受影响 Claim / 候选描述，再复核受影响项
    └─ 可选内容无法确认 → 移除该内容，保留创意主线
```

只在推荐方向的**关键知识确实失效**时才让 Creative 重新选择主线；其他候选不必同等深度地反复审核。预算到限时保留已完成的可靠成果，记录内部失败原因，不强行发布错误信息，也不将一次非关键搜索失败扩大为整次生成失败。

## 四、搜索成本、模型调用与运行效率

| 现有位置 | 建议变更 | 直接收益 |
|---|---|---|
| `research.py` | 先查项目内 Claim/Source；对基础知识直接生成并轻量复核；按实际缺口决定搜索 | 减少不必要的 Search/Fetch |
| `research.py` | 将重要发现信号保留给 Creative；避免靠重复研究寻找创意 | 提高单次研究价值 |
| `service.py` | 对 Research/Creative/Verifier 的调用设阶段性软预算，修订只针对失败部分 | 减少重复 LLM 调用和费用 |
| `search_client.py` / `store.py` | 复用已有结果与抓取正文；来源不可用时只在重要问题上尝试候补 | 减少重复抓取 |
| `package.py` | 选择足以支撑推荐方向的知识，不因 `required_claim_indices` 机械强制脚本逐条呈现 | 减少下游成本与内容僵化 |

原有 `RunOptions` 的最大调用数、超时等继续作为**防失控的工程上限**。不要把固定次数当作每次必须完成的调用任务，也不要为每次运行默认耗尽预算。运行耗时、模型调用量、搜索/抓取量、失败阶段等仅供研发使用，可记录到 RunEvent 中用于定位瓶颈。

**不为节省几次调用而牺牲最重要的内容**：当一次补研能决定整个方向是否真实成立时，允许在上限内投入；当知识已经足够且创意具有明确主线时，立即收束。

## 五、两种界面：面向创作者与面向研发人员

### 1. 用户体验的信息边界

| 时机 | 用户可见内容 | 仅研发可见 |
|---|---|---|
| 等待生成 | “正在了解主题”“正在寻找有趣的讲述角度”“正在整理内容”之类真实对应的进度描述 | Research/Creative/Verifier 调用顺序、API 地址、token、搜索次数、run_id、耗时明细 |
| 结果 | 推荐方向、核心看点、预期收获、其他适当候选、继续制作或调整方向 | 原始 Claim ID、证据 ID、模型 JSON、评分/风险分类、内部任务图 |
| 可补充的知识 | 简明解释与必要知识注意事项；用户主动询问时可提供来源或解释 | Evidence 映射、未核验草稿、数据库记录、原文切片、失败的抓取请求 |
| 可恢复问题 | “这次未能完成内容准备，可以重试或调整方向”；有部分可用结果时让用户继续选择 | HTTP 401/429/500、堆栈、原始服务异常、模型输出格式错误、内部重试和预算 |
| 反馈 | “这个方向不够有趣”“希望更直观”等人类可理解的反馈入口 | 技术性 Issue、状态流转、失败原因与定位信息 |

用户端不要展示 Agent 名称、JSON、URL 抓取进度、内部错误消息或研究日志；也不要出现“Verifier Blocked Claim C018”之类措辞。**对外用真实、简洁、可理解的产品语义，对内完整保存可诊断事实。**

外部来源和解释可以在用户明确需要时作为可选的“查看依据”呈现，但采用面向人的标题和说明，不默认铺开证据树，也不能无故承诺已经做过的核验。

### 2. 当前 Streamlit 页的职责

`backend/src/knowledge/devtools/review_app.py` 属于**研发人工检验工具**，不是对外正式产品。当前开发者仍需要查看 Claim、来源、错误和 API 事件，但不应把这一页的现有字段设计作为正式前端规范。

建议本地检验页提供两个明显不同的视图：

- **用户体验预览（默认）**：模拟普通用户的主题输入、生成进度、方向卡片、知识看点及自然语言反馈。无技术字段或报错泄露。
- **开发者诊断（明确切换后）**：可展开运行事件、耗时和调用量、Claim/证据、未核验知识、Search/Fetch 状态和异常细节。该视图仍限本机，不直接复用到生产 UI。

两者读取同一 `Run` 与 `KnowledgePackage`，**通过展示层转换，不复制两套业务状态或新增一套公开 Schema**。

### 3. 运行事件与异常的语义转换

保留原始内部事件和异常用于测试、日志与研发诊断；对用户提供一个统一的显示模型，例如 `stage_label`、`message`、`can_retry`、`next_action`。由专门展示适配函数映射，不在 Research/Verifier 的业务结果中混入用户话术。

- 检索、模型调用或数据处理的内部失败 → 用户看到“内容准备遇到问题，可以重试”，研发看到具体原因。
- 关键知识难以确认 → 用户看到“这个方向暂时缺少可靠信息，已为你保留其他可行思路”；研发看到 Issue 与证据缺口。
- 用户请求不明确 → 优先尝试有效默认配置；只有确实无法继续时才提供清楚的简短追问。
- 不显示虚构的百分比、剩余秒数、成功保证或未实际完成的步骤；内部重试在正常情况下不打断用户。

安全边界：不要把密钥、带凭据的请求、内部提示词或原始外部网页指令输出到用户界面；研发日志也应脱敏。

## 七、验证方法与验收标准

运行仓库现有验证命令，并扩展少量有针对性的回归用例：

```bash
# 仓库根目录、已安装知识层依赖
PYTHONPATH=backend/src .venv/bin/python -m pytest backend/tests/knowledge -q
.venv/bin/python contracts/validate_contracts.py

# 本机人工检验（必须使用真实 API 模式检查实际质量）
PYTHONPATH=backend/src STREAMLIT_SERVER_ADDRESS=127.0.0.1 STREAMLIT_SERVER_PORT=8501 \
  .venv/bin/python -m streamlit run backend/src/knowledge/devtools/review_app.py
```

建议人工检查以下情形，记录**是否可用、真实调用数量和实际耗时**，不强制做复杂对照实验：

1. **基础知识主题**（如“勾股定理”）：模型能直接产生并核查常见知识；无需为了每个基础定义都联网寻找证明，仍能交付合法知识包。
2. **需要具体依据的主题**（如指定年份的统计数据）：无法凭模型记忆确定时才检索；不能把未经确认的数据当作事实。
3. **创意优先的物理主题**：保留有价值的知识因果与可观察变化；不会因一个次要来源失败自动放弃整条创意主线。
4. **Attention 进阶主题**：方向清楚，适当解释计算机制；内容不退化为论文审稿意见或 PPT 知识点列表。
5. **异常模拟**（缺密钥、请求失败、预算用尽）：用户视图只看到清楚的操作提示，研发诊断仍能找到真实错误；不得泄露技术详情或误报已成功。
6. **重复输入**：同一项目内已有 Claim/Source 能被复用；不出现无价值的重复抓取和长循环。

验收重点：**推荐方向是否值得继续制作，用户是否能读懂并继续操作，时间/费用是否合理，事实风险是否得到恰当处理。** 所有测试通过只能说明工程路径稳定，不能代替这些产品判断。

## 八、完成边界

本次完成意味着知识层从“可运行的研究 Agent 系统”变成“能够低成本、稳定地为创作提供选题和知识的产品能力”。不要求增设 Agent、引入向量检索、重做正式前端或构造学术级事实认证流程。正式公共 Schema 如需更新，以与队友确认后的最小语义变更为准；其余内部调整优先独立在知识层完成。
