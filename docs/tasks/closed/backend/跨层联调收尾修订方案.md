## 二、已确定的产品与契约规则

1. **首版统一 16:9**：知识层缺省 `brief.effective.aspect_ratio="16:9"`；脚本和动画层据此采用 1920×1080 设计基准，实际预览等比缩放由对方负责。
2. **原始输入不可被静默覆盖**：`brief.user_input` 继续如实记录用户提交的比例。当前首版若收到显式 `"9:16"` 或其他尚不支持的比例，应在实际生成前明确告知“当前版本仅支持 16:9”，**不擅自改成 16:9**。
3. **Schema 保持通用**：`contracts/schemas/project-state.schema.json` 的比例字段采用通用形状校验，当前无需改成仅接受 16:9 的枚举；“首版支持范围”在业务入口检查。
4. **历史不回写**：已有 trials、旧产物、已发布 `ArtifactRef` 和历史记录中的 `"9:16"` 保留，不做批量迁移或覆盖。
5. **不增加用户负担**：当前本地检验页没有单独的画幅选项，因此无须为了本次改动增加一个配置表单。默认行为应直接满足 16:9。
6. **不新增 API 成本**：画幅约定是纯本地配置与校验问题；测试全部使用本地数据和假客户端，不应触发 DeepSeek 调用。

## 三、具体修改任务

### 1. 修改知识层默认配置（P0）

**文件**：`backend/src/knowledge/brief.py`

将：

```python
DEFAULT_EFFECTIVE = {
    "creative_mode": "visual_explain",
    "knowledge_depth": "balanced",
    "aspect_ratio": "9:16",
    "target_duration_ms": 165_000,
}
```

改为：

```python
DEFAULT_EFFECTIVE = {
    "creative_mode": "visual_explain",
    "knowledge_depth": "balanced",
    "aspect_ratio": "16:9",
    "target_duration_ms": 165_000,
}
```

保持原有 `build_brief()` 对明确输入和 `effective` 的一致性检查，**不要修改其他默认字段**。

预期：

```python
build_brief({"topic": "生日悖论"})["effective"]["aspect_ratio"] == "16:9"
```

若用户在原始输入中明确提交比例，`build_brief()` 仍忠实保留该值；具体支持范围由正式生成入口提前判断。

### 2. 在正式生成入口明确拦截不受支持的比例（P0）

**文件**：`backend/src/knowledge/service.py`

在 `generate_knowledge_package()` 中完成 `validate_brief(brief)` 后、创建 Run 与调用任何外部模型之前，检查：

```python
if brief["effective"]["aspect_ratio"] != "16:9":
    raise ValueError("当前版本仅支持 16:9 视频画幅。")
```

可用现有异常类型或小范围封装表达“暂不支持的画幅”，但**不必为这一项额外设计错误服务、状态机或新的公开 Schema**。

选择这一位置的原因：

- 能在计费请求前阻止首版尚未支持的输入；
- 不会改变 ProjectState Schema 对未来其他比例的兼容能力；
- 不会伪装成生成成功；
- 用户端只看到可理解的操作提示；研发端仍可保留具体异常信息。

实现后核对 `backend/src/knowledge/devtools/review_app.py` 的展示边界：普通用户不能看到 Python traceback、内部模块路径或原始异常；对比例不支持的情况可显示“目前只支持 16:9，调整后可继续”。本地检验页暂不新增画幅输入控件。

**注意**：如果实际项目已有统一的业务入口在调用知识层前完成此检查，可以复用该入口；但需要覆盖直接调用 `generate_knowledge_package()` 的情况，防止绕过统一入口后产生无意义 API 消耗。
