## 一、当前状态与修订范围

当前分支已经具备真实 DeepSeek 研究、定向补证、关键事实核查、知识包保存与导出，以及用户预览和研发诊断两种视图。现有测试和仓库 `STATUS.md` 记录了阶段性验收，但测试通过不代表生成效果达到最终产品标准。

需要处理的是以下有限几项：

| 优先级 | 问题 | 本轮决定 |
| --- | --- | --- |
| P0 | 低风险基础知识通过轻量检查，却因公共证据类型不支持而无法交付 | 协调一次最小 `internal_review` 契约扩展；保持真实审核，不伪造来源 |
| P0 | 顶层 `required_knowledge_refs` 从推荐方向的内部必要 Claim 直接映射，切换方向后冲突 | 调整语义与组装逻辑；默认空数组，不新增逐方向 required 字段 |
| P0 | 用户体验预览当前固定使用 Mock，任意主题无法真实生成 | 有密钥时明确使用真实生成；无密钥时明确标识示例，不静默伪装成真实生成 |

## 二、基础知识核验与可交付依据

### 1. 问题定位

现有 `verifier.py` 允许模型将常见、稳定、低风险的概念标记为通过轻量一致性检查；但只要不存在 `supports` 的内部 Evidence，Claim 仍会进入 `needs_review`，最终 `package.py` 无法将其作为已核实知识输出。

公共 `contracts/schemas/knowledge-package.schema.json` 又规定 `verification_status=verified` 必须有 `evidence_refs`，且 `evidence.kind` 目前仅支持 `external_source / mathematical_derivation / user_material`。这使得普通基础知识也可能为了找一条形式上的证据而反复调用 Search/Fetch，降低效率与可用性。

### 2. 确定的修订方式

**与共享契约负责人确认后，在 `evidence.kind` 中仅新增 `internal_review`。** 其语义是“系统已对稳定、低争议、低风险的知识做过简明内部质量检查”，明确**不是外部独立证据，也不是论文级的真实性证明**。

- 保留 `verified` 至少有一个 `evidence_refs` 的现有结构约束。
- `internal_review` 的 `title` 是人类可读的检查名称；`details` 是简短、具体的检查依据或适用条件，不要求填写虚构网址。
- 仅适用于基础定义、常见原理等不涉及争议或时效性的低风险主张。
- 具体数值、最新事实、研究结论、争议内容以及决定整条视频核心因果的高风险主张，继续使用真实来源或可复核推导；不能仅靠 `risk_level=low` 这一模型标签无条件放行。
- Verifier 在原有集中审核中作出判断，不为 `internal_review` 另增一次模型调用。
- 不用空洞的“模型确认正确”冒充检查依据；内部记录要能简要说明检查了什么，且不展示给普通用户。

例如“一个三角形具有三条边”可以按低风险基础定义检查；某实验的具体结果、某年人口统计或一个反直觉的科学结论不能依靠此类型直接交付。对真实可复核的数学推导，优先保留 `mathematical_derivation`。

### 3. 文件与数据流

1. `contracts/schemas/knowledge-package.schema.json`：`evidence.kind` 新增 `internal_review`，该类型要求 `details` 非空；其余形状尽量不变。
2. `contracts/接口契约与协作规范.md`：说明新增类型的适用范围，以及它不能与外部证据混为一谈。
3. `contracts/examples/`、`contracts/validate_contracts.py`：同步更新涉及该类型的 Mock 和检查。原有外部来源、推导案例仍应继续合法。
4. `backend/src/knowledge/models.py`：`ClaimEvidence.evidence_kind` 接受新类型；沿用现有 `relation`、`claim_id` 等字段。
5. `backend/src/knowledge/verifier.py`：只有在低风险且审核确实通过、未发现冲突时，创建对应的 `ClaimEvidence`，并把公开 Evidence 和内部 Evidence 同步关联到原 Claim。不得将 `revise / block` 状态直接写成已核验。
6. `backend/src/knowledge/research.py`：`_public_evidence` 能正确序列化已缓存的 `internal_review`；重复运行可复用已存在的合格核验记录。
7. `backend/src/knowledge/package.py`：正常组包并保持证据引用检查；不得绕过 Schema、填入不存在的证据 ID 或将普通模型来源假称数学推导。
8. `backend/tests/knowledge/`：覆盖常见知识无搜索可交付、核心高风险知识不能仅靠 `internal_review` 放行、跨项目引用不串用、导出与重新读取一致。

**修改共享 Schema 之前先征得队友同意**。如暂未协调完成，本轮内部修改可单独测试，但不可把未支持的 `internal_review` 写入公开包后声称跨层契约已达标。

## 三、方向约束与知识包语义

### 1. 修正 `required_knowledge_refs`

当前 `package.py` 将推荐方向的 `required_claim_indices` 转成顶层 `constraints.required_knowledge_refs`。但内部 `required_claim_indices` 表示“这个创意要成立，依赖哪些核心知识”；顶层字段的公开语义则是“当前视频必须呈现哪些知识”。两者不可直接等同。

同一个 KnowledgePackage 包含多个方向时，用户一旦选择非推荐方向，脚本层就可能遇到不属于所选方向的强制列表。

**决定：本轮不新增 `directions[].required_knowledge_refs`。公开的顶层 `required_knowledge_refs` 默认输出 `[]`。** 只有存在一条对包内所有可选方向都确实需要在成片中保留的共同知识、或者已确认的跨方向硬性内容要求时，才可加入。不能简单取推荐方向的核心主张，甚至不能只按知识 ID 交集机械决定“强制呈现”。

保留以下区别：

| 数据 | 含义 | 对脚本层的约束 |
| --- | --- | --- |
| 内部 `required_claim_indices` | 创意成立所依赖的知识前提 | 用于候选可行性与核验，不要求全部逐条出镜 |
| `directions[].knowledge_refs` | 此方向关联的、经核验的知识素材 | 作为脚本选材的主要范围 |
| `knowledge_units[].importance` | 核心、辅助、可选 | 用于优先级判断，不等于必须呈现 |
| `knowledge_units[].conditions` | 知识成立条件 | 只要采用相关知识，就不得违反 |
| 顶层 `constraints.required_knowledge_refs` | 所有方向通用且确实必须出现在本视频中的硬性内容 | 可以为空；只有真实的共同强制项才填 |
| 顶层 `constraints.must_not_misrepresent` | 跨方向应遵守的事实边界 | 不把某个未选方向的特有前提机械强加给其他方向 |

修改时将 `_importance` 的核心知识判断与顶层 required 数组解耦；保留关键 Claim 的条件与 `importance=core`，不要因 `required_knowledge_refs=[]` 意外丢失核心知识标注。

### 2. 选择与修订

- `ProjectState.decisions.direction_id` 是实际采用的方向；缺省时可使用 `KnowledgePackage.recommended_direction_id`，并写入相应系统默认决策。
- `ProductionScript.direction_id` 必须是知识包中存在的方向，并与项目当前决策一致。
- 脚本优先从所选方向的 `knowledge_refs` 取材；如有必要，允许利用同包其他**已核验**知识作辅助，不得擅自改换作品核心方向。不要强制所有知识都进入成片。
- 仅切换到已准备充分的其他方向时，更新项目决策和下游脚本即可；如果确实需要补研或改变知识包内容，再生成新的知识包版本。
- `required_knowledge_refs` 的范围、引用完整性与所选方向一致性需要加入测试。

### 3. 主要修改位置

- `backend/src/knowledge/package.py`：修改全局 required 的组装，保留 per-direction knowledge_refs、importance 和重要 conditions。
- `backend/tests/knowledge/test_package.py`、`backend/tests/knowledge/test_workflow.py`：增加两方向知识集合不同、改选非推荐方向、空 required 数组合法的测试。
- `contracts/接口契约与协作规范.md`：与队友确认后明确此语义；如 Schema 字段形状不变，不因该修订另造一份接口。
- `contracts/validate_contracts.py`：保留对 `required_knowledge_refs` 实际被脚本使用的验证，同时补测“选非推荐方向且全局 required 为空”应通过。

## 四、正式交付路径与精确版本

### 1. 选定交接方式

**本次双人黑客松按“版本化 JSON 文件”交给脚本层**。这是传输方式而非另一套公共字段。脚本层不依赖知识层 SQLite、内部 Claim、ResearchStore、RunEvent，也不需要调用 Research/Creative/Verifier。

现有知识入口与存储行为可以继续保留：

```text
KnowledgeService 生成合法 KnowledgePackage
  → ResearchStore.save_package 决定实际 revision
  → 将该版本以 JSON 写到 KNOWLEDGE_EXPORT_DIR
  → 导出成功、可以按版本重新读取
  → 协调器发布 ProjectState.artifacts.knowledge_package = {artifact_id, revision}
  → 脚本层读取被钉住的同一 JSON 版本
  → ProductionScript.knowledge_package_ref 原样引用它
```

导出文件命名沿用现有实现：`{artifact_id}-r{revision}.json`。实际导出目录由 `KNOWLEDGE_EXPORT_DIR` 统一配置，禁止消费者自行拼接不同设备的绝对路径。这里不建立 HTTP 端点，等真正需要跨服务部署再考虑。

### 2. 需要保证的交接不变量

- 以 `store.save_package()` 之后的 `artifact_id`、`revision` 为准；脚本层不得自己计算，也不得以“读取最新包”代替精确引用。
- 文件导出使用同目录临时文件和原子替换，避免脚本层读到只写了一部分的 JSON。对于已发布版本，不可用不同内容静默覆盖同名文件。
- 导出成功后进行最小读取/Schema 校验；**仅在文件可用后通知协调器发布该 ArtifactRef**。如果导出失败，保留错误供研发诊断，不发布指向不可读取文件的引用。
- 成功发布后，即使新知识包生成或修改，已有 ProductionScript 的 `knowledge_package_ref` 仍指向原版本。不能因“最新版”更新而悄悄改变既有脚本的基础知识。
- 若现有 `service.py` 顺序让运行状态已被标为完成、却因 JSON 导出失败而被回写为失败，需要调整为“保存成功—导出完成—发布可用”语义一致；已有数据库包不代表外部交付完成。
- 导出包仅包含公共 `KnowledgePackage`，内部运行记录仍保留为独立开发资料，不交给脚本层。

### 3. 可直接验证的用例

- 初次生成：保存后导出 `KP_…-r1.json`，包内 `revision=1`，JSON 通过校验。
- 重复提交无内容变化：可复用同一版本；引用不变化。
- 内容实际变化：新版本 `r2`，`r1` 仍可读取，旧脚本继续引用 `r1`。
- 导出写入异常：不能发布本次 ArtifactRef，脚本层不会读取半成品文件。
- 非推荐方向：`ProductionScript.direction_id` 指向选中方向，`knowledge_package_ref` 仍使用同一已发布知识包版本。

## 五、人工检验页与用户信息边界

### 1. 不改变双视图设计，只修复真实入口

现有 `review_app.py` 已区分“用户体验预览”和“开发者诊断”，应该保留。但当前关闭“显示开发者诊断”时 `mode_label` 固定为 `离线 Mock`，导致在普通预览页输入任意主题并不能真实研究。

修订后的约定：

- 在本地具备 `DEEPSEEK_API_KEY` 时，用户体验预览的“生成方向建议”触发**真实知识层主入口**；点击时发生 API 调用，不在打开页面时自动调用。
- 页面在执行前以简短的人类可理解提示说明“将使用在线模型生成，可能产生调用费用”，不展示 API、token、请求数等研发指标；避免无意识重复提交。
- 未配置密钥时，明确提供“离线示例体验”或提示配置，标明示例只覆盖固定主题；**不得把 Mock 输出当作任意主题的真实结果**。
- 开发者诊断仍可以显式选择 Mock / Real API，查看调用统计、来源和错误。普通预览只展示推荐方向、核心看点、学习收获及自然语言可操作提示。
- 无论来自哪个视图，都使用同一个 `generate_knowledge_package()`，不得复制业务逻辑。开发者切换视图后应能追查同一次 Run。

### 2. 不扩建失败审查工作台

- 普通用户不显示 HTTP 代码、原始 JSON、内部 Claim ID、模型输出异常、系统 Traceback 或 Agent 工作步骤。
- 失败时使用简短、准确的语义提示，例如“这次内容准备没有完成，可以重新尝试”，必要时给出“调整主题”入口。
- 技术错误和 RunEvent 留在开发者诊断中，保留已有人工备注和 JSON 下载功能。
- 失败页暂不新增大型 ResearchStore 浏览器；真正定位不了问题时再补最小诊断字段。

## 六、模型输出异常与创意发现的轻量修正

### 1. 一次有限的结构化输出恢复

仓库真实 API 验收曾出现模型 JSON / 字段形状无效。应区分两种失败：

- **语法无效**：无法解析 JSON、没有最终结构化文本或 JSON 被截断。
- **字段无效**：JSON 可解析，但角色对应的 Pydantic 模型无法接受，如必填字段缺失、输出形状错误。

建议先完善对应角色的输出约束与可容忍的字段归一化；确实遇到上述结构错误时，**只对当前失败的模型结果执行至多一次结构修复/重新生成**，向模型指出简短的字段错误，不重新执行前面的 Research、Search/Fetch 和 Creative。修复消耗计入 `max_model_calls`、Token 统计和耗时记录。超出预算或修复仍失败，则正常失败，绝不伪造默认知识包。

不得把 HTTP 身份验证失败、持续性网络故障、事实审核未通过当成“JSON 格式问题”反复调用模型。优先为真实出现过的格式问题加测试，避免写通用无限重试框架。

涉及：`llm_client.py`、调用角色的结构解析边界（`research.py` / `creative.py` / `verifier.py`）、`service.py` 的模型调用预算与测试。

### 2. 把 Research 的知识发现交给 Creative

`ResearchPlan` 已具有 `discoveries`，但 `ResearchResult` 与 Creative 的输入未完整消费该字段。最小修复是：

- 在 `ResearchResult` 中保留简短发现列表，初步研究和定向补研都可增补，去除重复项。
- Creative 的输入增加 `research_discoveries`，在现有知识主张上下文之外提供有价值的反直觉现象、因果变化或认知线索。
- 发现是**启发性线索**，不是可交付事实。只有关联的核心知识通过核验，才能作为正式方向依据。
- 不强制每条 Claim 产生发现；不新增单独的发现 Agent、复杂评分或新数据库表。

涉及：`research.py`、`creative.py` 和针对性测试。

## 七、环境文档的顺手修复

当前 `docs/work/backend/知识层技术栈路线.md` 使用 `uv venv --python 3.11 .venv` 后紧接 `python -m pip`。由 uv 创建的新虚拟环境不保证附带 pip。

```bash
# 方案 A：仍使用 python -m pip
uv venv --seed --python 3.11 .venv
source .venv/bin/activate
python -m pip install -r backend/requirements-knowledge.txt
python -m pip check
```

或全部使用 `uv pip install -r backend/requirements-knowledge.txt`。Windows 示例同步修改；不要为此迁移依赖管理体系。

## 八、执行顺序与验收

建议以**最小可联调闭环**排序：

1. **共享契约协调**：与队友确认 `internal_review` 和全局 `required_knowledge_refs` 的语义，获得认可后再修改 `contracts/`。
2. **P0 业务与包**：落实轻量内部复核合法交付、required/importance 解耦、精确版本 JSON 导出及发布顺序；给相应部分补回归测试。
3. **P0 用户预览**：修复默认 Mock，保证有密钥才能执行真实生成、费用提示清晰、错误不泄露内部信息。
4. **P1 小补丁**：只处理观察到的模型结构输出错误及 discoveries 传递；如本次联调成本很紧，可先完成 P0 再做 P1。
5. **P2 文档**：顺手修正 uv 示例；同步状态文档，不把未通过验收的功能写成已完成。
6. **人工验收**：检查至少一个普通基础知识主题、一个进阶机制主题、一个有明确 `must_include/focus` 的主题及非推荐方向切换；观察结果是否真的值得制作、耗时与调用是否可接受。
