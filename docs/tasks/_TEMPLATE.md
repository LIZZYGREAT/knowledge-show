# [任务名称：简洁描述预期结果]

> 用途：名称为 `tasks/open/YYYY-MM-DD-主题.md`。任务可按实际复杂度删减细节，不为套模板补写无价值内容。

## 一、任务信息

| 项目 | 内容 |
| --- | --- |
| 制定时间 | `YYYY-MM-DD HH:mm` |
| 审查分支 | `分支名`|
| 审查基线 | `commit SHA`|
| 任务类型 | 新增功能 / 错误修订 / 体验优化 / 性能优化 / 重构 / 集成联调 / 文档维护 / 其他（可多选） |
| 涉及人员 | A / B / 共同（按需填写） |
| 关联位置 | Issue、PR、对应设计文档或接口契约（没有则省略） |

## 二、任务目标与现状

**当前已有的事实**：简短说明已实现的行为、现有问题或依赖条件；区分已验证事实与推测。不要复述长篇讨论历史。

**本次需要完成的任务**：用明确的行为描述目标，包括必要的输入、处理与用户可见的结果。复杂任务可分为若干完整、可验证的小阶段。

**范围边界**：明确这次不做什么（仅在确实容易误解或扩大范围时填写）。

## 三、涉及文件与协作边界

| 文件 / 模块 | 预期操作 | 目的及边界 |
| --- | --- | --- |
| `path/to/module` | 新增 / 修改 / 仅阅读 | 说明它在本任务中的职责 |
| `path/to/shared-contract` | 可能变更 / 仅阅读 | 如涉及共享契约，先与相关负责人确认 |

> 路径为审查时的预期范围。Codex 可在目标内合理调整文件组织，但新增跨所有权修改、破坏性接口变更或重大架构变更，须先说明影响并取得授权；不能为了匹配表格修改无关文件。

## 四、建议实现方式

从已有代码入口说明怎么实现；写清关键步骤的**输入、处理、输出与依赖顺序**。可根据实际需要包含：

1. **准备与定位**：首先检查哪些现有代码、契约、配置和测试。
2. **主要实现**：关键的数据流、逻辑修改、接口或状态更新；必要时写伪代码或短代码片段。
3. **集成检查点**：若有多阶段工作，哪些阶段完成后应单独验证并形成一个 Commit。
4. **风险与降级**：只写实际可能阻塞本任务的关键风险，以及可接受的替代路径。

建议方式提供技术方向。只要保持目标、契约与边界一致，允许 Codex 在局部实现上选择更简单的方案；影响需求语义的替代方案须先确认。

## 五、验证方案与预期结果

| 验证项 | 操作或命令 | 预期结果 |
| --- | --- | --- |
| 功能主流程 | 实际运行、调用接口或完成 UI 操作 | 写出明确可观察的完成条件 |
| 回归 / 错误场景 | 对相关测试样本或异常路径执行检查 | 写出需要保持或纠正的行为 |
| 工程检查 | 现有的 lint、typecheck、测试或构建命令 | 按本任务风险选择，不为小改动强制全量执行 |

测试文件需要随新逻辑、缺陷修复和风险适度增补；如无自动化环境，写清人工验证步骤。**不可把计划执行的检查写成已经通过。**

## 六、结果对照审查

这是给 Codex 在交付报告中逐项回应的审查依据。**正式任务文件默认不回填执行流水和结果**；通过对照后再由负责人确认归档。

| 对照项目 | 修改前 / 审查基线 | 应达到的结果 | 审查方式 |
| --- | --- | --- | --- |
| 核心功能 | 说明原有行为或缺口 | 说明新的可观察行为 | 实际运行 / 测试 |
| 代码与接口 | 说明原有结构或问题 | 预期修改范围、契约保持或改变之处 | Diff / Schema / 调用方检查 |
| 关键回归 | 说明必须保持的既有能力 | 既有能力不受影响 | 对应测试 / 端到端检查 |

**交付时要求**：逐项报告“满足 / 不满足 / 未验证”及证据；列出实际修改文件、相关测试命令与结果、Commit（如已提交）和遗留问题。不要仅凭代码存在就声称验收完成。
