# 文档维护规范

> **目标**：让新开发者或 Agent 在最少阅读量下找到**当前有效**的信息。文档用于减少协作成本，不记录所有工作过程。

## 1. 信息分层与权威来源

| 信息 | 权威位置 | 维护原则 |
| --- | --- | --- |
| 项目目标、启动方式、文档导航 | `README.md` | 概述，不复制详细实现 |
| Agent 启动/执行/授权流程 | `AGENTS.md` | 精简、稳定、可执行 |
| 当前可用能力与活动任务 | `STATUS.md` | 当前快照，不积累历史 |
| 工程实现规范 | `docs/engineering.md` | 规则集中，允许合理例外 |
| 开发、测试、Commit 与交付流程 | `docs/workflow.md` | 日常执行流程集中维护 |
| 用户确认的产品与设计理念 | `docs/design-principles.md` | 用户主导维护；Agent 不擅自改写 |
| 指定操作的复用方法 | `playbooks/` | 按需检索，例如页面截图与视觉检查 |
| 共享 API 与数据契约 | `docs/contracts/` | 一份权威定义，必要时由工具生成 |
| 重要成果与改变 | `docs/CHANGELOG.md` | 只记录实质变化，不复述 Git 日志 |
| 当前技术架构/模块细节 | `docs/architecture.md`、`docs/frontend/`、`docs/backend/` | 只在实际复杂度需要时维护 |
| 已确认的具体实施方案 | `tasks/open/`、`tasks/closed/` | 当前待执行与已确认完成的方案；正文不追加执行日志 |
| 值得复用的故障知识 | `docs/lessons.md`（按需创建） | 只记已确认的根因、解决方案和预防办法 |

**事实与意图区分**：代码、运行结果解释当前实现；接口契约约束共享行为；已确认任务说明本次要实现的变化。三者冲突时要核验。

## 2. 按需详细化，不强制文档增殖

- 日常先读 L0（README、AGENTS、STATUS），再按任务读相关契约或规范。产品设计或页面体验任务才补读 `docs/design-principles.md`；需要特定操作时才读取相应 `playbooks/`。
- 总体数据流足够复杂时才创建 `docs/architecture.md`；单个模块存在重要、难以从源码理解的机制时才创建 `docs/frontend/xxx.md` 或 `docs/backend/xxx.md`。
- 前后端细节各由对应负责人维护；其他人可阅读，跨所有权修改时先协商。
- 文件开头写简短范围、关键入口文件和定位信息；标题能直接反映内容。`playbooks/` 只维护具体可重复操作，不再复制项目通用规范。
- 不复制粘贴同一份 API 字段、算法或配置到多个文档；引用当前权威来源即可。

## 3. 现行文档直接修订

- **替换或删除失效内容**，连同相关引用和图示一并修正；禁止在末尾不断追加“V2 修订”“最终补充”。
- Git 负责保存历史版本。正式文档应以**当前有效结果**为主，已否定的设计与调试过程不保留在正文。
- 日常无需记录中间失败。只有已查明根因、可复现或值得避免的典型问题，才选择性记录在 `docs/lessons.md`。

## 4. `tasks/` 的特殊规则

- **当前任务由用户明确指向，或由 `STATUS.md` 精确指向**。任务方案可参照 `tasks/_TEMPLATE.md`，包含审查时间/分支、类型、目标、文件范围、建议实现、验证与结果对照标准。由用户在 ChatGPT 确认后交付。
- 执行前核对任务与现有代码/现行契约是否相容；旧任务文档允许保留原样作为历史，不需要逐个添加“已完成”或“过期”标记。
- 已经确认执行完毕的 task 文档放置在 `tasks/closed/` 目录下，而尚未完成的任务放置在 `tasks/open/` 目录下；不需要进行维护合改写任务正文。
- 已落地成果写入对应正式文档；任务中的临时方案和中间试错不应回填正式文档。可以单独维护中间过程文档，但不应存在正式文档中。
- 无需为每个任务文档创建总结、设计文档或变更日志；执行结果在交付对话中按任务验收项对照报告，无需更新 task 正文。

## 5. 更新触发条件

| 实际变化 | 更新动作 |
| --- | --- |
| 局部样式、普通小 Bug、私有函数微调 | 通常无须更新文档 |
| 稳定功能范围或启动方式改变 | 更新 README 或 STATUS 的对应条目 |
| 共享字段、API 或对外语义改变 | 在同一任务中更新权威契约、相关调用与验证 |
| 模块边界、重要运行链路改变 | 更新现有架构/模块文档；必要时创建新文档 |
| 活动任务结束、任务交接、出现重要阻塞 | 更新 STATUS 的对应状态，移除失效活动项 |
| 达成重要里程碑或关键架构决策 | 增加一条简短 CHANGELOG，必要时附原因 |
| 用户确认核心产品与设计方向调整 | 由用户维护 `docs/design-principles.md`，直接修订现行描述 |
| 形成值得重复使用的实际操作方法 | 可选择更新/新增对应 `playbooks/`，不要求每次任务都写 |
| 发现典型可复用问题 | 可选：记录 lessons 的根因、修复及预防措施 |

**责任**：谁修改了对应代码，谁核对受影响文档；共享语义变更由相关负责人确认。每次任务只检查改动触及的文档，不扫描和重写整个 `docs/`。

## 6. 维护完成标准

- 现行契约、架构说明与实际结果不矛盾。
- 过期内容被原地修订或删除；不新增长篇补丁说明。
- 重要状态准确；历史任务未被误认为当前实现。
- 未触发更新条件时，不需要产生文档改动。
