# 开发、验证与交付工作流

> 本文是日常操作流程的权威说明；`AGENTS.md` 只提供启动和路由规则。目标是保证两人及各自 Agent **快速开发、持续可运行、可追踪修改**。按风险缩放步骤，不要求每个小修改都开 PR、写长报告。

## 一、接手任务

1. 查看 `git branch --show-current`、`git status --short`、最近一次提交，识别已有未提交改动；不得擅自清理他人工作区。
2. 阅读 `README.md`、`STATUS.md` 和**本次指定**的 `tasks/open/xxx.md`；若用户直接给出新指令，以其明确要求为准。禁止遍历全部历史任务。
3. 按需要查看相关代码、`docs/engineering.md`、共享契约和模块文档；设计与交互决策补读 `docs/design-principles.md`；特定操作可使用 `playbooks/`。
4. 确认目标、受影响文件、所有权、可验证结果。局部明确任务直接执行；涉及共享对外语义或其他人代码的修改，先同步范围和影响。

## 二、按可验证的功能增量开发

采用“**一个完整小目标 → 实现 → 局部验证 → 检查 Diff → Commit**”的循环，而不是积累大量代码直到最后才检查。

- 一个增量应具备可描述的功能或修复结果；不要求每编辑一个文件就提交。
- 实现新业务逻辑、修复已知缺陷时，优先添加或调整能验证该行为的测试。沿用仓库现有测试工具，不为一个小功能引入重型测试体系。
- 每个增量只改动本任务相关文件。发现无关问题可简短记录，不擅自扩张任务。
- 接口变更须与调用方、Mock、Schema 一致；共享破坏性变更先由相关负责人确认。

## 三、检查与实际结果

| 修改类型 | 建议的最小验证 |
| --- | --- |
| 文案、样式、小范围 UI 改动 | 相关语法检查；实际看目标页面 |
| 普通业务功能或错误修订 | 相关自动化测试；必要的类型/构建检查；关键行为验证 |
| API、共享数据结构、跨模块集成 | 契约检查、调用方检查、联调和相关回归测试 |
| 启动入口、部署、关键主流程 | 从可复现环境启动，执行主流程 Smoke Test |

- 测试需要真正执行，并记录**命令/操作及其结果**；未运行时写“未验证”和原因。
- 测试失败时先定位和修复；不要隐藏异常或将不通过写成已完成。若存在已知无关失败，应单独说明并避免误报整体通过。
- 测试文件可与代码一同提交；临时截图、调试日志和一次性数据默认不进入仓库。只有用户明确要求或确有复用价值时才保存。
- 不强制所有任务跑全量测试或追求特定覆盖率；验证深度应与风险相称。

## 四、Commit 与协作边界

1. 单个功能增量通过相应验证后，**及时 Commit**；多阶段任务允许形成多个清晰 Commit。
2. 提交前看 `git diff`、`git status --short`，按文件/代码块选择性暂存；避免 `git add .` 混入他人改动、密钥、构建产物。
3. 检查暂存差异 `git diff --cached`，确认只包含本次增量和被触发的文档更新。
4. 使用可读的提交说明，例如 `feat: add analysis preview`、`fix: handle empty response`、`test: cover retry failure`。建议标注出来A/B成员提交的，例如`feat-A：....`。
5. 尊重当前任务的分支要求及其他人的修改；不得自行 reset、clean、force push、改写共享历史。**Push、合并与发布按用户/团队已授权的流程执行**。


## 五、阶段收尾与文档同步

- 对照任务中的验收项，审查**预期行为与实际结果**，列出通过、未通过和未验证项目。
- 仅按实际变更更新权威文档：接口 → `docs/contracts/`；关键数据流 → 架构文档；稳定功能/运行方式 → README；重要进展和阻塞 → STATUS；重大成果 → CHANGELOG。详见 `docs/documentation.md`。
- **现行文档直接修订**，不叠加旧版本补丁。普通样式修改、小 Bug 和日常提交通常不产生文档更新。
- 最终交付保持简短：完成内容、主要修改、实际执行的检查及结果、Commit、遗留问题（如有）。
- **任务归档**：负责人与用户确认该任务已完成后，将对应任务文档从 `tasks/open/` 移入 `tasks/closed/`，不向原文补写过程记录。尚未确认则保持在 open。

## 六、双人集成的约定

- 个人负责的普通模块可独立开发；影响其他开发者的接口、共享状态、公共配置时，先说清“原行为 → 新行为 → 受影响方 → 切换时间/验证方法”。
- 不要求所有变更互相审批。共享语义变化由相关负责人确认。
- 每次结束一段较长的开发工作前，确保当前进展已 Commit 或明确保存于个人分支，并更新真正影响交接的 STATUS 内容。

> 本流程帮助完成工作，若某步骤对当前任务没有实质价值，可缩减；但不得跳过必要的契约确认、测试结果真实性与他人工作保护。
