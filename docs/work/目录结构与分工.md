## 二、工作区与修改边界

| 位置 | 主要负责人 | 内容 | 协作规则 |
|---|---|---|---|
| `backend/src/knowledge/`、`backend/tests/knowledge/` | 成员 A（知识层） | 需求理解、研究、候选生成、知识包输出 | 不直接修改脚本时间线 |
| `backend/src/script/`、`backend/tests/script/` | 成员 B（脚本层） | 选材、旁白、场景与时间线规划 | 不直接改写已核验知识事实 |
| `frontend/src/animation/` | 动画负责人 | 可播放场景及动画运行实现 | 不擅自改变脚本语义或知识事实 |
| `frontend/src/features/` | 前端负责人 | 用户输入、预览、修订交互 | 通过契约请求调用后端 |
| `backend/src/workflow/`、`backend/src/api/` | 共同商定后认领 | 状态、路由、接口胶水层 | 变动前通知对方 |
| `contracts/` | 双方共同维护 | Schema、Mock、校验 | **接口字段修改必须先协商** |

负责人标签仅用于划分默认修改范围；不强制一人承担该列的全部模块。每个人可以先独立完成自己的工作区，集成相关文件按任务认领。

## 三、保持简洁的约定

1. **代码与文档分离**：代码放 `backend/`、`frontend/`；接口 JSON Schema 放 `contracts/`；说明与决策放 `docs/`。
2. **一处权威源**：Schema 只存在于 `contracts/schemas/`；跨阶段语义见 `contracts/接口契约与协作规范.md`，传输端点登记于 `docs/work/contracts/API.md`，不复制字段。
3. **共享层尽量小**：只有双方实际共用的功能才放 `common/`、`workflow/`；不要为了抽象而提前拆包。
4. **测试紧邻责任范围**：知识与脚本各自测试分开，`integration/` 只做端到端和跨阶段检查。
5. **产物不要写入源码目录**：运行期生成的动画、视频、临时素材与日志放到可配置的数据位置并通过 `.gitignore` 忽略；等确定部署方式后再决定具体目录。
6. **任务保持平铺**：`tasks/open/` 与 `tasks/closed/` 已足够，通过文件名前缀（如 `knowledge-`、`script-`）标记责任，不必继续拆多级目录。
