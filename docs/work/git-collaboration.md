# 双人 Git 协作规范

> **目标**：以低沟通成本、可独立推进、及时集成和主分支可运行作为优先目标。规则应帮助开发，不因形式化审批、复杂分支模型或冗余检查拖慢进度。
>
> **适用对象**：两位开发者及其使用的 Codex / 其他编码 Agent。具体代码质量和文档维护规则分别遵循 `docs/engineering.md`、`docs/documentation.md`；本文件只规定 Git 协作和集成流程。

## 一、分支与职责

采用 **一个 `main` + 短生命周期任务分支** 的模式。

- `main`：当前可运行、可演示的集成版本。已知会破坏核心流程的改动不合入。
- 任务分支：针对一个明确功能、修复或配置任务建立；完成、验证并合入后结束，不长期堆积。
- 分支名以用途区分：`feat/upload-ui`、`fix/api-timeout`、`chore/setup-ci`、`docs/update-api`。命名应能理解任务，不强制包含日期、姓名或任务编号。
- 前后端或其他模块可以分别设置主要负责人。**所有权约束修改权，不限制阅读权**；各自模块内的常规实现可以独立推进。

双方可以同时从 `main` 开分支。尽量按模块或文件划清并行范围，避免两个 Agent 在同一工作区、同一个共享文件上同时编辑。

## 二、哪些改动需要沟通

| 改动类型 | 默认协作方式 |
| --- | --- |
| 自己负责模块内的功能、局部修复与合理重构 | 自主完成、验证并提交 |
| 不改变既定行为的注释、样式及简单文档修订 | 自主完成，允许简化 PR 流程 |
| 改动双方共用的 API、数据格式或接口语义 | 先告知受影响的一方并确认契约，再实现 |
| 修改对方负责的代码 | 说明原因、文件范围和影响，取得对方确认 |
| 变更根目录配置、关键依赖、启动方式或部署入口 | 提前同步，必要时双方各自验证环境 |
| 删除数据、强推、重写共享历史、覆盖他人未提交修改 | 必须得到明确授权；默认不执行 |

接口变更沟通只需要说明 **原行为 → 新行为 → 受影响的调用方 → 谁负责同步修改**。达成一致后更新 `docs/contracts/` 中的权威契约；不再维护一份重复的聊天版接口说明。

出现阻塞时先通过一句简短消息说明需要对方做什么，避免无关的长篇状态汇报。若共享修改无法及时确认，优先推进不依赖它的任务。

## 三、日常开发与 Commit

### 1. 开始任务

在自己的工作目录中执行：

```bash
# 查看现场，避免覆盖他人或上一任务的未提交内容
git status --short
git branch --show-current

# 在工作区允许切换分支时，从最新主分支创建任务分支
git switch main
git pull --ff-only origin main
git switch -c feat/short-description
```

预期结果：当前位于新任务分支，起点是最新 `main`。如果工作区已有未提交改动，应先确认归属、保存方式及与当前任务的关系；**不得为了切换分支直接丢弃、清理或重置这些改动**。

### 2. 开发过程中

- 完成一个**有意义且经过对应检查的增量**就及时 Commit，例如接口可用、组件完成、一次修复通过。无需按固定时间或每修改一个文件就提交。
- Commit 仅纳入当前任务的文件。优先显式 `git add <文件路径>` 或 `git add -p`，避免不检查就执行 `git add .`。
- 信息简短、可理解，例如 `feat: add upload interaction`、`fix: handle empty analysis result`、`docs: clarify API response`。
- 可以在同一任务分支上提交多次；阶段完成后及时 Push，降低丢失工作和临时交接的风险。

```bash
git status --short
git add <本任务的文件路径>
git diff --cached --stat
git commit -m "feat: implement upload UI"
git push -u origin feat/short-description
```

预期结果：暂存区只包含本任务改动，Commit 创建成功，分支已推送到远端。若还没有完成一个稳定增量，可以继续开发，不必强行为凑 Commit 提交不可运行的内容。

### 3. 同步 `main`

短期任务尽量在数小时或一个明确功能阶段内完成；持续时间较长时，在合入前同步最新主分支：

```bash
git fetch origin
git merge origin/main
```

以上命令在**任务分支**执行。默认使用普通 Merge，同步过程尽量避免不必要的 Rebase 和强制推送。发生冲突时，先判断重叠改动的真实意图，涉及队友负责的逻辑要一起确认；禁止仅为消除冲突而整段覆盖另一方代码。

## 四、PR、检查与合并

**默认为正式功能和修复创建 PR**，用于查看差异、触发 CI 和快速集成。极小、低风险且双方无并行冲突的修改，可以经协作约定直接进入 `main`，无须机械创建 PR。

PR 内容只需覆盖：

1. 完成了什么、涉及哪些模块。
2. 执行过哪些检查，结果为通过、失败还是未执行。
3. 是否改变共享接口、是否需要另一方配合；有未解决问题时如实列出。

### 按风险审核

- **常规任务**：本人确认差异、相关检查通过后即可请求合并；不强制另一人逐个审批。
- **跨模块 / API / 公共配置变更**：相关负责人确认影响和必要联调后合并。
- **高风险变更**（关键数据流、认证、持久化、部署入口等）：双方确认关键路径可用后合并。

**推荐 Squash and merge**，使 `main` 的历史按任务聚合。PR 合并前应确认：核心行为符合任务、相应验证完成、共享影响已处理、需要更新的现行文档已同步。合入后可删除已完成的远端任务分支；不要清理其他人的活动分支。

> **Agent 权限**：允许 Agent 创建任务分支、修改本任务文件、运行检查、提交自己的改动以及按授权 Push/创建 PR。**合并到 `main` 由人确认操作**；强推、删除共享分支、覆盖他人改动不得自行进行。

## 五、轻量 GitHub CI

技术栈确定后，在 `.github/workflows/` 配置**一个简单的 CI 入口**即可。建议针对 PR 和 `main` 推送运行：

- 对应语言的快速语法、类型或 Lint 检查。
- 现有的轻量单元测试与构建检查。
- 涉及接口变化时，执行已有契约/调用方验证（若已建立）。

CI 对前端和后端分别运行必要检查；无关模块不必重复耗时执行。开发初期先让 CI **报告结果**，运行稳定后再考虑将可靠、快速的关键检查设为合并门禁。CI 失败时应修复实际问题，不得修改检查以掩盖失败。

## 六、合并后的协作与项目状态

1. 合并后，发起人简短告知对方：**进入 `main` 的能力、可供调用的接口、尚需配合的事项**。若没有共享影响，不必专门发送长通知。
2. 需要双方参与的功能，在最新 `main` 上走一遍真实端到端路径；只有相关功能需要联调，不要求每次都做全量回归。
3. 阶段性更新 `STATUS.md`：保留活动任务负责人、当前分支、集成目标与重要阻塞；不记录每个 Commit。
4. 已落地的 API、架构或启动方式变化，由修改者根据 `docs/documentation.md` 更新现行文档；过时内容直接改掉，不叠加 V2/V3。重要里程碑才记录 `docs/CHANGELOG.md`。

**最终原则：能独立完成的任务就独立完成；会影响对方的改动提前同步；自动检查替代重复劳动；规则本身不能成为额外的开发负担。**
