# knowledge-show 核心产品与设计原则

> 此处只保留跨模块应长期遵守的稳定决策。完整背景、用户输入体系和内容工作流见 [产品理念与工作流共识](design/产品理念与工作流共识.md)。知识层内部研究、创意探索、核验及收敛机制见 [知识层探索与创意策划](backend/knowledge/知识层探索与创意策划.md)。跨阶段字段以仓库根目录 `contracts/` 为准。

## 一、服务对象与作品目标

创作者可能对知识主题尚不熟悉，也没有编剧、动画或剪辑经验。系统应主动承担选题探索、知识准备与制作责任，让用户通过**选填的创作要求、可选的推荐方向和自由反馈**参与创作。最终观看者看到的是一条**线性播放、时长通常约 2 分 30 秒至 3 分钟**的知识视频；制作过程中通过真实可播放的动态预览确认效果，再导出成片。

作品追求**愿意看下去的吸引力、鲜明而连贯的观看体验、清晰的视觉重心和有价值的知识发现**。关键事实与重要前提必须准确，但不以讲完全部知识体系、堆砌材料或进行论文式论证为目标。知识是否可靠与视频是否好看、好懂，是需要共同满足的两个方面。

## 二、输入与创作自主性

- 主题是唯一必填项；知识细化方向、创作模式、创意想法、必须包含/避免的内容、知识深度、美术偏好、画面比例均可选填。
- **创作模式与美术风格解耦**：模式描述偏好的讲述方式（创意优先、直观演示、干货精讲、故事悬念），美术偏好描述画面审美；知识深度是独立维度。模式是方向偏好，不是固定的叙事模板。
- 系统可以探索并推荐候选方向，但**首次生成前不强制用户选择**；用户可以提前确认，也可以直接采用系统推荐生成可播放预览。
- 用户明确提出的内容和偏好必须保留；补全默认值不能覆盖明确要求。用户无需承担专业知识审核或了解内部 Agent 工作流。

## 三、知识驱动的创作原则

- **主线先行**：一条视频应围绕值得关注的问题、发现或机制变化推进。内容之间需要有认知或因果联系，避免把互不相干的知识点拼在一起。
- **知识推动叙事**：真实规律应当影响故事、实验、观察、条件变化或结果；可以没有人物故事，也可以有出人意料的情节，但不能只在普通剧情中插入一段科普说明。
- **明确的视觉对象与重心**：观众应能持续追踪重要对象、状态或关系，知道正在看什么、为什么发生变化。抽象量、数据和数学关系同样可以成为真正的视觉对象。
- **自然连续、具有原因的变化**：让状态更新、关系改变、对象运动及结果形成连续可理解的过程；避免突兀替换对象、割裂切换和缺少知识意义的表面运动。
- **明确排除 PPT 式动画**：不能把一串标题、文字、公式、图表或静态知识卡片，通过淡入、平移、翻页和转场包装成主要动画内容。文字与公式可以辅助表达，但作品必须有真实、可感知、与知识机制相关的视觉变化。
- **创造力不等于固定形式**：探索、比较、实验、幽默、故事和严密的直观演示都可以成立；不规定角色、情节反转、知识数量或固定段落。真正的创意应体现在知识怎样影响观众的观察和理解。

## 四、分层交付与研究原则

- **知识层**通过研究与创意的双向探索，形成具有实质差异的方向、可靠知识、必要前提及创作潜力。知识既可以由模型已有知识产生，也可以来自可复核推导或外部检索；进入正式可用素材前要按风险核验。知识单元数量由主题和用户目标决定，不预设额度。
- **内部研究知识统一管理**：资料来源、知识主张、证据、未解决问题和创意线索应能够关联、检索与复用。Agent 先使用已经研究的内容，有具体缺口时再补充外部搜索；未经核验的猜想不作为确定事实传给下游。
- **核验服务创作**：重点处理核心事实、重大误导和必要条件。遇到可修正问题，优先帮助创意以正确方式成立；不把每一条基础知识都审成论文，不让 Verifier 决定审美、故事形式或镜头安排。
- **脚本层**选择和重组知识，设计贯穿全片的认知及事件主线、场景和时间推进；不被知识依赖顺序或知识单元列表机械绑定。
- **动画层**自主构建具体视觉对象、关系和连续运动，让知识变化真正可见；知识层对外只描述知识问题与视觉潜力，不强制给出分镜、角色、镜头或动画示例。

## 五、反馈与工程取舍

- 用户先看**实际可播放的动态结果**，再反馈和导出；静态分镜或 Schema 通过不能替代真实观看体验。
- 支持对片段、事件或时间范围的自然语言反馈，优先定向补充研究与局部修订，保留可靠的已有成果。
- 阶段产物与内部对象使用稳定 ID、版本和引用；公开契约负责跨层交接，内部知识管理方式不强加给其他成员。
- 研究适时收敛：**找到值得制作的方向、具备足够知识支持、没有阻碍交付的关键事实问题即可推进**，不为凑数量、评分或反复核验拖慢产品。
- 黑客松阶段优先形成“**输入主题 → 自主探索/可选确认 → 脚本 → 可播放预览 → 反馈修订 → 导出**”的闭环。工程结构和审查流程应尽量轻量、可用，不能让用户为复杂架构买单。
