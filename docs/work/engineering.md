# 代码实现规范

> **目的**：减少阅读、修改、调试和跨人协作成本。按风险使用规则，避免为了“规范”进行无意义重构。

## 1. 模块与依赖

- 一个模块应有清晰、可描述的职责；相近且共同变化的逻辑放在一起。
- API/交互入口与核心业务逻辑尽量分离；复杂度很低时允许直接实现，不强制增加层级。
- 模块之间通过明确接口传递数据，不依赖其他模块的私有状态、未约定内部结构或隐式副作用。
- 只有真实复用、独立变化或降低认知负担时才抽象。拒绝无意义的 Manager/Factory/Adapter 链、只转发调用的包装层和预设未来需求的复杂框架。
- 避免一次功能修改牵动许多无关文件；发现大量跨模块同步修改时，先评估职责边界。
- 尽量避免硬编码，可以单独维护配置层方便设置修改。
- 修改范围围绕当前任务。

## 2. 规模与复杂度：软阈值

| 指标 | 提醒检查 | 明显需要说明理由的情况 |
| --- | --- | --- |
| 普通业务文件 | 约 300–400 行 | 超过约 500 行并持续增长 |
| 普通业务函数 | 约 40–60 行 | 超过约 80–100 行且承担多个步骤或职责 |
| 条件嵌套 | 多于约 3 层 | 主要执行路径难以追踪 |

连续算法、布局、生成文件和必要的集中配置可以合理例外。重点检查是否存在职责混杂、重复规则、过多隐式依赖与难以局部验证的状态更新。

## 3. 适度防御与错误处理

- 在**信任边界**校验外部输入、文件、网络返回和持久化数据；已经验证的内部数据不逐层重复校验。
- 对外部服务使用合理超时、明确错误处理，确有需要时才使用**有限重试**。
- 不写无条件的 `except Exception: return {}` 等静默兜底，不制造虚假的成功数据。
- 失败时尽量保留原始错误原因；只有确有恢复路径时才增加 fallback。
- 不预先构建多级兼容层、过度边界分支或未经需求支持的复杂容错体系。

## 4. 注释与日志

- 注释重点说明**为什么**如此设计、不可见的不变量、算法关键步骤与外部限制；避免复述代码字面行为。
- 修改实现时同步修改或删除失效注释；不留下“临时”“待删除”等过时解释。
- 运行日志聚焦核心状态变化、关键请求/任务、耗时、外部服务失败及可定位的异常信息。
- 避免循环刷屏、重复打印、未经控制的调试输出；不记录密钥、Token、密码及不必要的用户原始数据。
- 不保留无关的临时代码、调试开关或无意义注释。

## 5. 修改与验证

- 优先复用现有库；新增依赖应有明确用途，及时更新锁文件及环境说明。
- 局部修改执行相关检查；接口/共享数据变更检查调用方；关键流程或集成阶段执行 Smoke Test。
- 如无法验证，说明未验证的原因；不得用“应该没问题”代替结果。
- 不为低风险样式修改引入大规模测试和审查，也不因软阈值强制拆分清晰代码。
